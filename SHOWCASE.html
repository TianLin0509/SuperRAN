以前每验证一个无线通信 idea，都要从零搭一遍信道仿真——参数怎么配、数据怎么存、PDP/PMI 怎么算，每个人写得都不一样，结果无法横向对比。

现在一句话就能拿到数据，而且拿到的是物理量，不是别人裁剪过的训练特征。

你说想验证什么→ Agent 问 3~6 件关键的事→ 落一份计划书→ 生成 + 给取货代码

一、四条设计铁律

① 不传数据，传取货代码

单个信道样本几百 KB，序列化成 JSON 会膨胀到十几 MB——进不了任何模型的上下文。所以 MCP 只回句柄、统计摘要，和一段能直接跑的 Python。

② 给物理量，不给训练特征

PDP 不归一化、RSRP 不截断、SRS 给完整协方差和全部特征值、PMI 给码本索引而非嵌入向量。绕开为表征学习裁剪过的那条路。

③ 生成与取货解耦

测量量都是从信道现算的。半小时后想起还要 PMI？重新取货，实测 1 毫秒，不重跑仿真。

④ 先问实验设计，再问参数

参数配错重跑就行，实验设计错了整个结论作废。所以先问"跟什么比、用什么指标"，再问信道模型和天线数。

CDL-A 的能量集中度只有 CDL-C 的四成——方法对散射丰富度是否敏感，一测便知。视距比例则确实只能靠站间距拉开（0.458 vs 0.125）。

这里有个坑，是实测中发现的。直觉上"想对比视距/非视距就跑 CDL-C 和 CDL-D"，但实测两组数据逐比特相同。

根因：仿真器按几何逐链路判定视距与否，如果你选的剖面类别和判定不符，它会自动替换成同类别的默认剖面（非视距→CDL-C，视距→CDL-D）。所以在非视距链路上选 CDL-D，实际用的还是 CDL-C。

这个行为文档里没写。MCP 现在会在提问时直接讲明，并把对比组建议改成"改站间距"——那才是真正能改变视距比例的旋钮。

三、想改信道生成逻辑，要动多少东西？

这是设计时就考虑的问题：末端阵子结构、PMI 权、PDP 权这些迟早要改。结论是分四层，绝大多数改动落在最外两层，主体不动。

之所以能做到，是因为四件事彼此独立：信道怎么生成（ChannelHub）· 测量量怎么算（measure.py）· 该问用户什么（decisions.py）· 有哪些现成场景（presets.yaml）。改其中一个不牵动其余三个。

L0 · 零改动 —— 纯配置透传已实测验证

什么情况：ChannelHub 已经支持的能力，只是没默认开启。

例子：1驱3 / 1驱6 子阵结构、每 RF 口的阵子数与间距、馈电幅度相位、固定下倾、天线方向图（波瓣宽度 / 增益 / 交叉极化比）、端口映射顺序、有效子阵 vs 物理阵子建模模式。

怎么做：在 overrides 里写进去就行。superwireless 对不认识的键原样透传，不做解释也不拦截。

场景 6 就是这一层——改动 0 行代码。

L1 · 改一个 YAML —— 沉淀成预设presets/presets.yaml

什么情况：L0 那套配置每次都要手写太麻烦，想固化成"我们的标准 AAU"。

怎么做：在 presets.yaml 里加一个条目，把整块阵列配置塞进 config。之后用户说"用我们的 AAU 配置"就能命中。

不碰任何代码。加射线追踪城市场景也在这一层。

L2 · 加知识 —— 让 MCP 会问这件事decisions.py

什么情况：新参数会实质影响结论，希望 MCP 主动问用户而不是等用户想起来。

例子：加一个决策点"末端合并方式（1驱3 / 1驱6 / 独立端口）"，写清楚 why——合并会降低垂直自由度、栅瓣位置随子阵间距变化；再配一条护栏"做垂直维波束赋形时若选了 1驱6 要提醒自由度不足"；还可以加一个对比组"1驱3 vs 独立端口"。

改动范围：往三个列表里各加一条（ALL_DECISIONS / TASK_PROFILES / 可选的 _DESIGN）。纯数据，无逻辑改动，不影响任何已有任务类型。

L3 · 加算法 —— 新测量量或改算法measure.py + 三处登记

什么情况：要新的物理量，或者现有算法要换口径。这是你问的"PMI 权 / PDP 权"落点。

你想改什么动哪个函数会牵动谁
PDP 换算法（加窗、改时延分辨率、按天线分开）power_delay_profile()只有它。PMI/SRS 不受影响
PMI 换码本（Type II、eType II、自研码本）type_i_codebook() 旁边加新函数 + pmi_type_i() 加分支只有 PMI。PDP/协方差不受影响
PMI 换搜索准则（容量最大化替代匹配增益）pmi_type_i() 内的度量式只有 PMI
协方差换加权（IIR 滤波、按 RB 分组）spatial_covariance()只有 SRS 那组量
加一个全新测量量新函数 + 三处登记不影响任何已有量

加新测量量的三处登记：目录 MEASUREMENT_CATALOG（让用户能查到）· 自然语言别名 _ALIASES（让用户能点单）· 取货代码片段 deliver._BLOCKS + loader 的一个方法。

这一层是唯一需要真写算法的地方，但每个测量量是独立函数，改一个不会波及其他。

什么情况下必须动 ChannelHub

只有一种：你要的物理效应 ChannelHub 根本没建模。比如末端合并要引入互耦、或者要按实测 Jones 方向图（而非参数化方向图）建模。

这时改的是 ChannelHub 的信道生成内核，superwireless 侧通常仍是零改动——它只负责把配置传下去、把结果接出来。除非新增了需要单独暴露的物理量，那就顺带做一次 L3。

已经踩过的一个坑，值得记住

做这次扩展性验证时发现：superwireless 的抽象参数 bs_antenna（当时用来表示 "64T4R" 这种简写）和 ChannelHub 的 bs_antenna 配置块重名了——后者正是 1驱3 子阵的落点。结果阵列配置被静默吞掉，不报错。

已改名为 antenna_preset，并保留字符串写法的向后兼容。教训：抽象层的参数名不能和被封装层撞车，这类冲突只有真去传一次配置才发现得了。

六、已知约束

  • 信噪比不能直接设定。它由路损、发射功率和撒点位置决定。要求特定区间时走拒绝采样，可能很慢或取不到；想整体调整，改发射功率或站间距更有效。
  • 视距比例不由信道剖面决定。见场景 1 的说明——靠几何控制。
  • 射线追踪拿不到逐径几何。ChannelHub 尚未把 Sionna 的 Paths 对象导出到数据契约，所以射线追踪数据集会拒绝 ds.paths()（而不是返回假角度）。
  • QuaDRiGa 未纳入，它需要 MATLAB/Octave 运行时。

物理计算内核来自 ChannelHub，射线追踪基于 Sionna RT，工作流设计参考 superpowers 的 brainstorm → plan → execute 三段式。

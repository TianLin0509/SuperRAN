一、干扰强度怎么量化：IoT

用户说"高干扰场景"时，"高"是个数，不是形容词。业界的口径是 IoT（Interference over Thermal，噪声抬升）：

IoT = (I + N) / N —— 干扰加噪声比纯热噪声高出多少。 现场约定：20 dB 以上算高干扰。

它能翻译成很直观的东西。上行极点容量关系 IoT = 1/(1−η) 把 IoT 换成等效小区负载：

IoT3 dB6 dB10 dB13 dB20 dB30 dB
等效负载50%75%90%95%99%99.9%

一个会让所有结论偏几十 dB 的坑

教科书上 IoT = SNR / SINR——因为 SNR = S/N、SINR = S/(I+N)， 相除正好是 (I+N)/N。但在这套引擎里不能这么算。

字段信号项噪声项
snr_dB接收功率，不含阵列增益 全带宽噪声，还额外减了 10log10(RB)
sinr_dB（几何 SINR） rx · N_ant · |wHa|²，含阵列增益 全带宽噪声

两者差一个 10log10(RB) + 10log10(N_ant·bf) 的定标偏差—— 273 RB、64 天线时约 40 dB。相减得到的数形状对、随场景变化的趋势也对， 只是整体偏了几十 dB，拿它当 IoT 会把中等干扰场景报成"极高干扰"。

正确做法是只用同一口径的两个量。sir_dB 与 sinr_dB 都出自同一次几何计算、共用同一个 S：

SINR = S/(I+N)、SIR = S/I，同一个 S
1/SINR − 1/SIR = N/S
IoT = SIR / (SIR − SINR)   （线性域）

于是 IoT 完全由已落盘的两个字段决定，不需要额外仿真。 自检：给定 (S, I, N) 直接构造三个量，公式与 (I+N)/N 的最大偏差是 1.1×10−14 dB——机器精度。

二、一个必须分清的边界：业务域 vs 测量域

业务域（traffic）

PDSCH/PUSCH 承载数据时受到的干扰。决定吞吐、MCS 选择。

量化用 IoT。

测量域（measurement）

SRS / CSI-RS 导频受到的干扰。决定信道估计精度，进而决定预编码好不好、CQI 准不准。

量化用导频域 SIR 与估计 NMSE 下限。

实网里最难查的一类问题正是：业务域 SINR 看着还行、测量域已经崩了—— 预编码用的是被污染的信道估计。两个配对场景把这件事量化了出来：

srs_congested 邻区 24 UE 同发、comb 2、无组跳 29.08 dB15.57 dB92.76 dB / 0.46 −10.50 dB 测量已失效
srs_clean_reference 邻区 2 UE、comb 4、开组跳 29.02 dB14.60 dB92.76 dB / 0.46 +7.37 dB 测量严重受损

两组只差导频配置：拓扑、功率、频点、天线、撒点全部相同， 路损中位数与视距比例逐位相同。 业务域 IoT 只差 0.06 dB（噪声），测量域却差了 17.9 dB。

只看业务域 SINR 会认为这两个场景是同一件事。

测量域的量只在 link="BOTH"（paired）时才产生—— 单向链路的数据里根本没有 ul_sir_dB / dl_sir_dB 这两列。 之前 superran 也没收集它们，所以"SRS 被邻区打穿"这类场景在数据里完全看不见。

三、哪些旋钮真的能动 IoT

下面每一条都是在这套引擎上真跑出来的（21 小区 UMi_NLOS、64T、 100 MHz、每档 42 样本），不是照搬教科书直觉——其中两条与直觉相反。

旋钮方向实测注意
isd_m 站间距调小 → IoT 升100 m 38.3 / 200 m 24.9 / 500 m 4.4 / 1732 m 0.2 dB作用范围最大。代价：同时改变 SNR，做对照组会混两个变量
tx_power_dbm 发射功率调大 → IoT 升33→49 dBm：24.9 → 40.9 dB，正好 +16；SIR 15.84 一动不动dB 对 dB 线性。抬 IoT 而不改 SIR 分布的干净手段
noise_figure_db / bandwidth_hz噪声底降 → IoT 升NF 7→3 dB：+4.0（理论 +4）；带宽 100→20 MHz：+7.0（理论 +6.99）两者都精确到 0.01 dB
num_sites 站数调大 → IoT 升3 小区 5.3 / 21 小区 24.9 / 57 小区 33.1 dB耗时按小区数近似线性增长（21 小区 444 ms，57 小区 920 ms）
pdsch_load / prb_utilization对下行完全无效0.2 与 1.0 两组的 SINR / SIR / IoT 逐位相同与直觉相反：每个邻区都无条件贡献泄漏，负载只决定对几个波束取平均
pusch_load × 每小区 UE 数调大 → 上行 IoT 升每小区 1 个 UE：无差别；每小区 5 个 + 满载：上行 IoT 0.7 → 5.4 dB调度 UE 数是 max(1, 每小区UE数 × 负载)，取整后常年是 1
num_interfering_ues主要影响测量域10→24：上行 IoT 0.71 → 0.69（无变化）；但 12 个就能把 SRS 测量 SIR 打到 −2.4 dB与直觉相反。且它是耗时大头：设 0 比设 10 快 1.62 倍

负载调不动下行干扰，这一条最容易踩。 几何模型里每个非服务小区都无条件贡献一份波束泄漏， pdsch_load 只决定对几个波束取平均——均值不变，只是方差变小。

后果很具体：拿它做"轻载 vs 满载"对比会生成两批一模一样的数据， 然后得出"负载不影响性能"。每一步都合理，结论完全是工具造成的。 现在 sr_plan 的 guards 会直接拦下来， 建议的扫描维度也已经从 prb_utilization 改成 isd_m。

两件实测出来、原本没料到的事：

① indoor_factory 的 IoT 是 46.9 dB——100×100 m 厂房里 4 个 AP 按 50 m 间距摆，彼此距离和到 UE 的距离同量级，干扰极强。 这个预设一直在，但没人量过它有多干扰。

② multicell_19site（57 小区）的 IoT 低于 multicell_7site（21 小区）：14.7 vs 27.2 dB。 不是站数的作用，是 ISD——19 站预设用的是 500 m，7 站用 200 m。 站数与站距一起变时，站距赢。

做干扰消融时，对照组怎么选

想问"干扰强弱对我的算法有多大影响"，需要两批只差干扰的数据。 在这套模型里 IoT 与 SNR 无法完全解耦——两者都含热噪声 N， 拉大站间距降 IoT 会同时把 SNR 拉低。实测对比两种对照组的做法：

对照组做法IoT 差SNR 差能不能用
拉大站间距（ISD 150 → 800 m）35.8 → 1.8 dB（34 dB） 29.4 → −5.9 dB（45 dB） 不能 两个变量一起变了
只减站数（7 站 → 1 站，小区尺寸不变）35.8 → 20.3 dB（15.5 dB） 29.4 → 30.5 dB（1.1 dB） 可以 变量分离干净

所以 low_iot_reference 定义成"同小区尺寸、去掉邻站"。 代价是剩下 2 个同站扇区仍互扰，IoT 只降到 20.3 dB——按现场口径这仍然算高干扰， 所以它的名字是"去邻站对照"而不是"低干扰对照"。名字要对得上实测值。

五、场景探测：下单前先看货

生成一批全带宽信道要几十分钟；但"这个场景到底长什么样"是几何量， 和信道矩阵的频域分辨率无关。同一 seed 下把 num_rb 从 273 压到 24 甚至 12：

量num_rb 改变后
sinr_dB / sir_dB逐位相同
pathloss_dB / distance_3d_m逐位相同
is_los / rx_power / doppler_hz逐位相同
ue_position、上行几何 SIR逐位相同
snr_dB差 10log10(RBfull/RBprobe)

唯一变的 snr_dB 是因为它的定义里显式带了 −10log10(RB)。 273→24 实测差 10.56 dB，与 10log10(273/24)=10.559 吻合到小数点后两位——可以精确还原，不是近似。

但修正有个前提，这是实现时踩的坑。 ChannelHub 把 snr_dB 夹到 ±50 dB。探测口径下 snr 高了 10.4 dB， 高信噪比场景会先撞上 +50 天花板再被减回去，得到一个看起来正常的假值—— 实测 InF 与密集城区两个完全不同的场景，探测出的 SNR 都是 39.5 dB（= 49.9 − 10.4）。 现在撞顶的样本会被剔除并单独报数。SINR / SIR / IoT 不受影响，它们不含 10log10(RB) 项。

符号数也能压，但有一道悬崖

num_ofdm_symbols（默认 14）同样只在内部用于导频栅格与平均， 存下来的信道是 [1, RB, BS, UE] 一个快照。实测降到 7 / 4 / 2 时 上面那张表里的量同样逐位相同——但降到 1 时 sir_dB 直接偏 16.1 dB。

所以 PROBE_NUM_SYM 取 4 而不是 2：离悬崖两格，不贴着边站。 2 已经验证过没问题，但只要 ChannelHub 内部任何一处对符号数的假设动一动， 2 就可能跟着塌——而这种塌陷不报错，它只是给出一组看起来正常的错数。

这个旋钮只对探测模式安全。正式生成里它实打实地改信道矩阵 （14→7 时 h_true 相对差 2.5×10−2，14→1 差 4.3）， 所以它只在 probe() 里，不在 generate() 里。

探测模式的正确性依赖 bs_panel。 缺 panel 时 ChannelHub 建不出 DFT 码本，几何 SINR 整条路径被跳过、sinr_dB 退化成 snr_dB， 而后者带 −10log10(RB)——于是压 num_rb 会让"SINR"整体平移 10.56 dB。

这个坑极其隐蔽：那时 sir_dB 是 49.9 哨兵、逐位相同，路损/距离/多普勒 也逐位相同，只有一个字段偏，看起来像探测模式本身不可靠。 写这一节的测试时就先踩了一次——参照组没补 panel，比的是两个都错的东西。 probe_config 现在自己补齐。

探测给不了谱效、吞吐、时延扩展估计、宽带预编码——24 个 RB 只覆盖 8.64 MHz（不是稀疏采样 100 MHz）。返回里的 not_available 会列清楚。

六、运行速度：哪些"优化"是真的

第一版基准测出 2.55× 的"免费加速"，是假的。 变体一个接一个顺序跑，耗时单调下降（4830→4054→…→1591 ms）， 那是预热与缓存，不是配置的作用。

重测方式：每轮把所有变体各跑一次，轮转 4 轮取中位数， 并把基准自身的轮间波动一起报出来——低于这个波动的"加速"就是噪声。 本机基准波动 11.9%。

八、已知局限

  • 没有 RMa 路损模型。 ChannelHub 只实现了 UMa / UMi / InF 三套 38.901 公式。 大站间距场景用的是 UMa_NLOS 配农村的站间距，属于"大站间距宏站"， 不能叫 3GPP 农村场景——RMa 的路损、阴影标准差、视距概率都不一样。预设里写了 caveat。
  • IoT 与 SNR 无法完全解耦。 两者都含热噪声 N。靠拉大站间距降 IoT 会同时把 SNR 拉低（实测 ISD 800 m 时 SNR 中位数 −5.9 dB），那样的对照组混了两个变量。 low_iot_reference 改成"只减站数、不动小区尺寸"，是能想到的最干净的做法。
  • 上行几何 SIR 靠钩子取。 ChannelHub 算出了它但没存进 ChannelSample， 只能包一层暂存下来。包装函数自带自检——把暂存里的下行量和样本自己的 sinr_dB/sir_dB 对一遍，对不上就返回 nan。 宁可没有上行 IoT，也不给错的。
  • 测量域 SIR 是 ChannelHub 在导频位置上算的功率比，不是解调后的实测 EVM。 它给出的是估计 NMSE 的下限，实际 NMSE 还受插值、平滑、MMSE 先验影响。
  • 探测模式只支持 internal_sim。 射线追踪的耗时由光线数与场景几何决定， 压 num_rb 省不下来，没有便宜的探测版本——调用会直接报错说明，而不是给一份 慢得跟正式生成一样、还标着"探测"的报告。

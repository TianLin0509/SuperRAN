一、为什么必须补这一层

这个项目的定位是"你提一个无线算法优化思路，在可信的信道上跑蒙特卡洛"。 但在这轮之前，那个思路的代码进不来。

sr_compare_arms 的 method 只认六个值： svd / svd_wideband / type1 / dft / mrt / identity。

也就是说：内置预编码之间能互相比、能过三道门、能拿到可引用的结论句； 而你自己的 CSI 压缩、信道估计、波束管理、定位、调度算法， 一个都进不去。要用门控就得先把算法改写成内置预编码之一——这显然不成立。

换个说法：门控这套东西的价值在于"拦住站不住的结论"， 可它之前只能拦内置基线之间的比较。而真正需要被拦的， 恰恰是你自己那个新想法——因为对自己的方法，人总是更容易宽松。

四、三道校验，以及为什么统计查不出错位

注册时锁死三件事，任一不成立就硬拦截，不是告警。

校验比什么不成立的后果
同一数据集 / 内容一致dataset_id + channels.npz 的 SHA-256 数据被重新生成过，两臂其实跑在不同信道上
样本顺序一致sample ID 逐个按序比，不只比长度 第 i 个数不对应同一个信道实例，配对前提崩塌
指标与单位一致metric + metric_unit 谱效跟 NMSE 比，没有可比性

把顺序打乱一个位置，p 值一模一样。实测：

差值Wilcoxon p有效吗
ID 对齐+1.3691.63e-11有效
ID 交换了第 0、1 位+1.3691.63e-11无效

统计层面完全不可观测。检验只看两个数值数组，根本不知道第 i 个数 对应哪个信道实例。所以错位只能靠 ID 契约拦——这不是多余的谨慎， 是唯一能拦住它的地方。

拦下来之后的输出：

门 2 拦截: ['样本顺序一致']
  样本数相同但 ID 序列不同，首个差异在第 0 位
  （ds_29bd7d92#0 vs ds_29bd7d92#1）；集合相同，只是顺序被打乱了

statement: 我的方法 与 顺序乱了 **无法比较**，未过门：样本顺序一致、前置条件。
           统计检验已跳过——错配数据上的 p 值没有意义。

顺便：register 拒收含 nan/inf 的值。 配对检验会把非有限值整行丢掉，两臂样本数悄悄变少，而 p 值照样算得出来。 所以宁可在注册时当场报错，也不要让它流到统计里。

默认情况下 register 自己生成 ID，两臂都用默认就一定对齐。 只有你显式传 ids=（跳过部分样本）时才可能出错——那时校验就是最后一道防线。

五、预注册：主指标是事先定的还是挑出来的

三道门证明不了这一件事。

真实过程往往是这样：跑完发现平均谱效没提升，顺手换成 5% 边缘用户谱效， 发现有提升，于是报了这个。每一步都合理——边缘用户谱效本来就是个 正当指标。但合起来就是在多个指标里挑赢的那个，而挑选本身会把假阳性率 推高到远超 5%。

做法：生成之前写下来，算个摘要

身份什么时候结论句怎么写
primary与预注册主指标一致 "结论成立（预注册主指标，pr_xxx）"
secondary预注册时列的次要指标 可以报，但主结论要用主指标
exploratory没登记过的指标 "统计上成立，但这是探索性分析，不是预注册主结论"
unregistered数据集没绑预注册 "结论成立（无法证明主指标是事先定的）"

实测：同一批数据换指标

把上面那次的指标从 spectral_efficiency 换成 edge_user_se（预注册里没登记），数字完全一样，但结论句变了：

我的方法(边缘) 相对 基线(边缘)：edge_user_se 13.329 vs 11.960 bit/s/Hz， 差值 +1.369（+11.4%），95% CI [+1.198, +1.541]，n=60， Wilcoxon 符号秩检验 p=1.63e-11。统计上成立，但这是探索性分析， 不是预注册主结论——预注册的主指标是 spectral_efficiency，这里用的是 edge_user_se。只能作为探索性分析报告……跑完再换指标等于在多个指标里 挑赢的那个，假阳性率远高于 5%

探索性不等于不成立。它统计上可能非常显著——上面这例 p=1.63e-11。区别只在能不能当主结论。

想把新指标升为主结论：重新预注册把它定成主指标， 然后用新数据验证。拿同一批数据换指标不算独立验证。

刻意做得很轻

做了

一个 JSON、一个确定性 SHA-256、不可原地改（改主意就新建一个 ID，旧的不动）、 生成时随数据存档、比较时判身份。

没做

版本树、审批流、不可变存储、多重比较自动校正。那是临床试验的量级， 个人做算法验证用不上——加上去只会让人绕过它。

只能在生成前绑定，没有"给已有数据集补绑"的接口。 预注册的全部价值就是"这是看数据之前写下的"，事后补绑只是记录，不是预注册。 所以那个接口不存在，也不该加。

未绑定时身份是 unregistered 而不是 primary——没登记过就不能声称主指标是事先定的。

六、谁负责什么（边界）

MCP 负责 superran

生成可信信道 · 出观察量 · 校验配对前提 · 跑统计 · 判门 · 判预注册身份 · 写结论句

你负责 你的脚本

算法本身 · 在自己进程里跑 · 保证预编码只看 h_est · 在 metadata 里声明口径

MCP 绝不执行用户代码。一旦它开始 exec 传进来的字符串， 就从"数据供应站"变成了任意代码执行面。用户代码在用户自己的进程里跑 （那本来就是他们的脚本），只把标准化的逐样本结果注册回来。

由此带来一个不对称：外部结果的 CSI 口径只能靠声明。

内置 compare_arms 能查两臂用的是 h_true 还是 h_est，因为预编码是它自己跑的。外部结果不行——MCP 看不到你的 函数里用了哪个。所以门 2 只能查 method_metadata 里的声明， 查不到就给 warn 并说清"这条得你自己保证"，不假装查过了。

两臂声明的口径不同时会被拦；确实要测 CSI 误差的代价， 在 metadata 里写 varies=["csi"] 声明即可放行。

逐样本值不进 MCP JSON。值落 .npz，MCP 只回句柄与统计摘要 ——和信道数据同一条规矩。实测 sr_compare_results 的完整响应 3768 字符，不含 values 字段。

七、新增接口一览

4 个 MCP 工具（总数 16 → 20）

工具作用
sr_lock_analysis 预注册：生成前把主指标、基线、CSI 口径、期望效应写下来，返回 prereg_id 与摘要
sr_export_eval_template 导出评测脚本骨架，替换一个函数即可；不改也能跑
sr_compare_results 判决两个外部结果：配对校验 + 门 2 + 门 3 + 预注册身份 + 结论句
sr_list_results 列出已注册结果与预注册记录

sr_generate 新增可选参数 prereg_id。

2 个新模块

模块行数内容
results.py~430 ResultArtifact、register、check_pairable、 dataset_digest、sample_ids、评测脚本模板
analysis.py~230 Prereg、lock、verify、classify、指标单位表

八、已知局限

局限为什么怎么应对
外部结果的 CSI 口径查不了 MCP 不执行用户代码，看不到函数内部 门 2 查 method_metadata 的声明并如实说明查不了；用户自己保证
算法正确性不查 MCP 只收指标值，不知道那个值是怎么算出来的 门控管的是"比较公不公平、统计站不站得住"，不管算法对不对
没有多重比较校正 做了会引入一堆需要用户判断的选择（族定义、校正方法） 预注册限定一个主指标，从设计上减少多重比较；其余标探索性
预注册不能事后补绑 这是有意的——事后补绑不是预注册 下次生成前先锁。已有数据集用 unregistered 身份，如实标注
样本 ID 只是下标 <dataset_id>#<i>，依赖数组顺序稳定 配 dataset_digest 一起用：数据变了摘要就变，能查出来

这轮之后，"我提一个算法思路 → 在可信信道上跑蒙特卡洛 → 拿到经得起推敲的结论" 这条路对自研算法是通的了。门控的标准和内置基线完全一致—— 用的是同一套 paired_compare 与 gate_conclusion。

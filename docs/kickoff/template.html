03 / FIRST TEN WORKING DAYS

首两周只承诺一个可验收案例

D1 是本人实际开工的第一个有效工作日。假期、出差与既有工作按实际出勤顺延，会上确认日期，不把日历周当成满负荷工时。

D1—D2 / 接入与定题

知道研究什么

安装、最小案例、站点上报；确认问题、参考来源、条件与边界。

交：一页约定＋一次可核验上报。

D3—D5 / 首个校验

先让参考站得住

用小场景核对已知关系。发现缺口先保留失败例，拆成小改动。

交：可重跑案例，或明确失败证据。

D6—D8 / 独立复跑

让搭档再跑一次

交配置、版本、命令和结果；复核不只读作者总结，必须自己核对证据。

交：复核差异与处理结果。

D9—D10 / 五分钟演示

能解释，能交接

本人说明问题、参考、结果和局限；决定继续研究、补底座或缩小范围。

交：报告＋下阶段明确动作。

后续六周：第3—5周做研究与小步扩展；第6—8周做独立复现和集中验收。未完成的能力列清楚，按实际证据决定发布范围，不预先承诺版本号或算法收益。
04 / DAILY COLLABORATION

每天怎么做，代码怎么交回来

网站同步进度；Git 保存代码版本；独立审核决定改动能否进入主干。三者各有一件明确的事。

参与者日常动作交给下一位什么
任务负责人讲清无线问题，确认实际条件，检查物理解释；遇到跨模块分歧及时提出。问题与验收要求、对结果的解释。
自己的 Codex隔离实现、小案例、自测；保存版本和证据；有实质变化时主动上报。代码提交＋可复跑报告＋站点回执。
公司 agent（GLM）在可访问环境核对 Airview、标准及内部参考；按现有合同给出具体问题和反例。问题清单、依据与最强反例；当前回路不直接接收公司侧 patch。
独立审核会话重新读改动并亲自运行；依据风险档分物理、集成等角色；核对代码版本。通过或必须修正的问题。换一个模型本身不等于完成独立审核。
合并执行者只接纳亲验通过的具体版本；主干变化后重验；失败交回原作者修正。新主干版本与影响说明。实现会话不能合并自己写的改动。

一次工作，按这个顺序走

读约定→查能力→做小案例→实现与自测→独立复核→合入或返修
  1. 需要改代码时，用 worktree：同一仓库中的隔离工作目录。先确认测试导入的是自己的代码。
  2. 一次改动只解决一个清楚的问题；共享接口先和受影响任务沟通。
  3. 参考不匹配时保留反例，不放宽测试、不偷偷换近似。
  4. 研究结束、代码合并、版本发布分别标明。负结果可以结题。

不同电脑：先集中合并

首轮建议：成员本地提交 → 通过约定渠道交代码包 → 中央仓库导入候选分支 → 独立会话执行现有合并闸门。

  • 代码包用 git bundle，保留提交历史与版本指纹；不是覆盖主干的压缩文件。
  • 主干始终是 develop；main 仅在维护者明确发起发布时更新。
  • 日常不自动推远端、不建 PR（远端合并申请）。未来私有远端按单独授权接入。
  • 跨电脑通道尚需会前联调；公司快照审阅仍按现有问题清单回路执行。
复核按现有风险规则执行：红档要有 Physics（物理）与 Integration（集成）两个独立审阅角色；黄档一个；绿档做相关检查。修物理问题，既要证明修复后通过，也要证明原版本能被新测试抓住。
给 agent 的代码交接要点（人员无需手敲命令）

完整 SHA 是代码版本指纹。下列尖括号为待填项；由 agent 先核对实际路径、分支与基线，不照搬占位符。

作者：读 AUTHOR.md → 隔离实现 → 自测 → 本地提交
记录：git rev-parse HEAD
记录：git rev-parse develop

跨电脑（会前先用小改动演练）：
git bundle create <交付包.bundle> <任务分支> ^<共同基线完整SHA>

接收方：
git bundle verify <交付包.bundle>
git fetch <交付包.bundle> refs/heads/<任务分支>:refs/heads/incoming/<姓名-任务>
核对导入后的完整 SHA 与交付说明一致；不强制覆盖已有同名分支。

独立 Merger 在中央主工作目录按 MERGER.md 执行：
python scripts/merge_task.py <候选分支> --expected-head <任务SHA> --expected-trunk <主干SHA> --dry-run
只有亲验 PASS，才对同一组 SHA 执行正式合并；主干或任务变化就重验。

公司 GLM：读 SYNC.md 的内网回路，返回“问题＋物理论据＋最强反例”。
网页不是代码交接通道，不上传私有接入配置或内部源代码。
05 / EVIDENCE AND UPDATES

一份交付材料，一条持续更新的记录

先使用网站已有的标题、负责人、状态、进展和成果链接。任务书放进自己的交付材料；网页尚未提供独立任务说明字段，不必等它才能开始。

每次上报，只说四句话

已完成：做了什么。 已验证：验证方式、结果与证据位置。 当前阻塞：需要谁确认哪件事。 下一步：下一个可验收动作。
  • 开始工作、有实质进展、遇到阻塞和交付时更新。
  • 返回 work_id 后保存到任务笔记；换电脑或 agent 仍沿用。
  • 拿到服务器成功回执才能说已同步。网页手改内容需明确交回 agent。

示例仅示范格式：已完成固定场景；已验证配置一致；阻塞是参考参数缺失；下一步请搭档核对原文。不要虚构完成比例。

交付时，能回答这五个问题

  1. 研究的问题、条件和本次范围是什么？
  2. 参考答案从哪里来，为什么适用于这个场景？
  3. 别人用哪份代码、配置和命令能复现？
  4. 谁独立复核了什么，还没证明什么？
  5. 哪些改动已合并，哪些只是本地实现或研究结果？

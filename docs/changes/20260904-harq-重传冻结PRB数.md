# 2026-09-04 HARQ — 重传冻结的是 PRB 数，不是 RBG 个数

**分支 / SHA**：`fix/harq-retx-prb-identity-20260904` / `<提交后回填>`　**风险档**：红
**报告**：`C:\VibeData\Artifacts\Reports\SuperRAN\20260904-harq-retx-prb-identity.html`

## 改了什么物理机制

HARQ 重传的资源身份。以前 `_HarqTb` 冻结 `(mcs, rank, n_rbg, tb_bytes)`，重传时
按优先级顺序取前 `n_rbg` 个可用 RBG。现在额外冻结 `n_prb`，并由新的
`_retx_indices()` 按优先级挑出**PRB 数正好等于冻结值**的那组 RBG；凑不出精确值
就把这次重传推迟到下一个同类型时隙，而不是换个大小发出去。

同时把发送路径上的重传身份校验从 `(mcs, n_rbg, rank, tb_bytes)` 改成
`(mcs, n_prb, rank, tb_bytes)`——决定 TBS 的是 RE 数，也就是 PRB 数。

## 为什么

Type-0 分组在 51 RB 这类带宽下首尾组不足名义 P：`rbg_prb_sizes = (8,8,8,8,8,8,3)`。
只冻结 RBG **个数**时，首传落在 3 PRB 的尾组、重传落到 8 PRB 的普通组，同样是
"1 个 RBG"，TBS 却从 672 B 变成 1793 B——**一个 TB 在重传时变了大小**，
而 BLER 仍按冻结的 MCS 从 NewTx 曲线查。这违背本项目"重传时空口 MCS / rank /
TBS 全部冻结"的模型合同。

代码里本来就有一道 `current_tbs != pending.tb_bytes` 的硬校验，所以后果不是
静默错误而是运行时崩溃。它在 `develop` 上是**潜伏**的：等长分组（绝大多数配置）
永远不会触发，51 RB 配置也要正好赶上重传与首传落在不同大小的组上。

## 证据

- 直接反例（在 `develop` 主仓库代码上跑，不含本次改动）：
  `TbsLookup.build(7, 8, 0.7, rbg_prb_sizes=(8,8,8,8,8,8,3))`，
  D 时隙 MCS23 / rank2，1 个 RBG 时尾组 TBS=672 B、普通组 TBS=1793 B，**差 2.67 倍**。
- 棘轮测试 `tests/test_scheduler_p0.py`：
  `test_retransmission_reproduces_the_frozen_tbs_on_an_uneven_carrier`
  （频选 / 非频选两个参数）。把 `_retx_indices` 换回 `ordered[:n]` 后实测变红，
  报错正是 `original=672 B, current=1793 B`；恢复后 5 passed。
- 等长分组不变性：`test_retx_indices_is_bit_identical_to_head_slice_when_groups_are_equal`
  对 17×16 的默认栅格逐 n 断言与旧的 `ordered[:n]` 逐位一致。
- 回归：test_system / test_physics_invariants / test_csi_aging / test_rng
  （`__main__` 入口，退出码 0）；test_scheduler_p0 19 passed、test_scheduler_edf
  45 passed、test_linkadapt 4 passed。ruff 仅剩 2 处 `develop` 上已有的告警。

## 没证明什么

- **没有验证 MU 配对下的重传**。`_build_mu_plan` 走另一条路径，本次只改了 SU 路径；
  MU 的重传由 `pending_ready` 前置排除（`if sched.mu_enabled and not pending_ready`），
  但没有为它写针对性用例。
- **没有量化"推迟重传"的吞吐代价**。凑不出精确 PRB 时本次选择跳过该 UE 这一 TTI，
  没有测量在高负载 + 不等长栅格下这会让重传平均多等几个 TTI。
- **贪心选择不保证最优**。`_retx_indices` 按优先级顺序贪心累加，遇到
  "跳过一个大组才能凑出精确值" 的组合不会回溯；当前 Type-0 的尺寸集合
  （若干个 P 和一个尾组）下这不构成问题，任意尺寸集合下可能次优。
- 没有改 38.214 允许的"重传可以用不同 PRB 数、TBS 不变"的真实行为——
  本项目的模型合同就是冻结资源，本次是让实现与该合同一致，不是靠近标准。

## 影响哪些 KPI

等长 RBG 配置（默认 `rbg_prb_sizes=None`）**逐位无变化**，已由不变性测试锁定。
不等长配置（51 RB / Configuration 2）此前会崩溃或（若绕过校验）虚增重传 TB，
现在重传吞吐可能略降——**未量化**。

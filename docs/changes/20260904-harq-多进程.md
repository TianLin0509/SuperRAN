# 2026-09-04 HARQ — 两条主循环都改为 N 进程（默认 8）

**分支 / SHA**：`feat/harq-multiprocess-20260904` / `<提交后回填>`　**风险档**：红
**报告**：`C:\VibeData\Artifacts\Reports\SuperRAN\20260904-harq-multiprocess.html`

## 改了什么物理机制

`capacity` 主循环的 HARQ 进程模型。改前每个 UE 只有一个槽位
（`harq_pending: dict[int, _LegacyHarqTb]`），发出一个 TB 后要等 ACK/NACK 回来
才能发下一个；`DDDSU` 下逐相位要等 2~6 个 TTI。

改后每个 UE 有 `SystemConfig.harq_max_processes` 个进程
（默认 **8**；38.213 §5.3 下行上限 16；设成 1 精确退回旧行为）：

- `harq_inflight: dict[ue, dict[harq_id, TB]]` + 每 UE 一个有序空闲 id 池
- 发新传时从池里取最小的空闲 id；ACK 归还；NACK 不归还，状态转 `retx_ready`
- 反馈处理**遍历该 UE 的每个在途 TB**——`DDDSU` 下 t0..t3 发出的 4 个 TB 会在
  t5 同时到期，一个都不能漏
- 候选筛选从 `u not in harq_pending` 改为「有空闲进程能发新传 **或** 有同类型
  时隙的重传就绪」
- 重传优先与「重传只能回同类型时隙、MCS/rank/TBS 冻结」的规则原样保留

## 为什么

单进程让 UE 在等自己反馈的时候完全发不出东西。它不是"待补的半成品"里那种
无害简化——`DDDSU` 下一个 UE 每发一个 TB 就要停 2~6 个 TTI。

## 证据

### `max_processes=1` 与旧实现**逐位一致**

8 组场景（n_ue ∈ {1,2,4,12} × {full_buffer, ftp3}）的结果指纹在改动前后完全相同
（排除新增的元数据键与被重写的合同字符串）。这是回归保护，不是"看起来差不多"。

### 收益的实际形状与任务书的估计**不同**

| 场景 | 1 进程 | 8 进程 | 变化 |
|---|---|---|---|
| full_buffer, 1 UE | 98.76 Mbps | 354.43 Mbps | **+258.9%** |
| full_buffer, 2 UE | 223.37 | 408.16 | **+82.7%** |
| full_buffer, 4 UE | 405.46 | 405.46 | +0.0% |
| full_buffer, 12 UE | 379.65 | 379.65 | +0.0% |
| ftp3, 12 UE | 218.65 | 219.34 | +0.3% |
| cbr-20M, 各档 | — | — | +0.0% |

**任务书说的「12 UE 吞吐提升 15~25 个百分点」在本仿真器里不成立。** 原因是
capacity 与 experience 的主循环都是**全带调度**：一个 TTI 本来就只服务一个
UE（或一对 MU），被反馈挡住的 UE 会被别人顶上，所以只要有 ≥4 个 UE 排队，
小区吞吐就不受进程数影响。上界可以直接量出来——把反馈时延整个关掉
（`harq_feedback_delay=False`）在 4/8/12 UE 下也只有 −0.0%/+0.1%/+0.6%。

`harq_feedback_wait_skips` 从 6000+ 降到 **0**（4 个进程起），机制本身确实接通了。

### 真正被单进程压住的是**用户体验速率**

`experience` 路径同一 ftp3 场景，1 进程 → 8 进程（这是**本次实现的结果**，
不是用开关量的上界）：

| | n_ue=4 | n_ue=12 |
|---|---|---|
| 体验速率中位 | 118.7 → **353.3 Mbps（+197.7%）** | 94.9 → **232.1 Mbps（+144.5%）** |
| 体验速率 p5 | 100.3 → **301.3 Mbps** | 77.3 → **173.8 Mbps** |
| 完成时延 p50 | 38.3 → **11.5 ms** | 41.5 → **21.0 ms** |
| 完成时延 p95 | 70.8 → 25.5 ms | 109.8 → 66.7 ms |
| 小区吞吐 | 67.2 → 68.2 Mbps | 206.6 → 207.8 Mbps |

小区吞吐几乎不动，是因为它 **offered-limited**：话务喂多少就发多少，
被 HARQ 挡住的 UE 会被别人顶上。**体验速率才是被单进程压住的那个量。**

`DDDSU` 下 **4 个进程就够**（8 与 4 逐值相同），默认 8 是留余量。

### DDDSU 下 4 个进程就够

已调度 TTI 数随进程数：`{1: 2, 2: 4, 4: 8, 8: 8, 16: 8}`（10 个 TTI 的最小夹具）。
默认 8 是留余量，不是必需。

## 没证明什么

- **依赖前一个 PR 的记账口径。** experience 侧的多进程必须建立在"buffer 在发送时
  扣减"之上：按 ACK 扣减时，被 NACK 的 TB 其字节仍留在队列里，同一个 UE 的另一个
  进程会把同一批字节再发一遍，原 TB 的重传随后就会硬失败。这条依赖是实测撞出来的，
  不是设计时想到的。
- **没有验证 MU 配对下的多进程重传**。`_build_mu_plan` 走另一条路径；有重传就绪时
  MU 本来就被禁用，但没有为"多个进程同时就绪 + MU"写针对性用例。
- **没有建模 RV 序列**（RV0/RV2/RV3 轮转），按任务书要求不做。
- **没有改 K1 时序**。当前取的是"第一个可用上行机会"，即**最小 K1**，
  与 38.213 §5.3 Table 9.2-7 的查表值有差距——真实 K1 只会更大，
  所以本模型的反馈比现场快、OLLA 收敛也偏快。已在 `amc_policy` 与 CLAUDE.md
  写明。
- **没有量化多进程对 OLLA 稳态的影响**。已观察到一个真实交互：进程放开后
  UE 发得出 3 倍的 TB，MU OLLA 收到的反馈也多 3 倍、偏置爬得更高，实发 MCS
  的预测 BLER 更容易越过 0.5 的配对准入线，于是 MU 占比从 0.38 掉到 0.17、
  `mu_pair_rejects` 从 95 涨到 733。**这不是 bug**（已由 17.2d 显式钉住），
  但"OLLA 步长是否要随进程数重新标定"没有做统计判决。
- 没有测 `max_processes` 与 CSI 老化、SRS 跳频的交叉场景。
- 进程数上限 16 是按 38.213 §5.3 写的，**没有验证** 16 进程下的内存/耗时代价。

## 影响哪些 KPI

- UE 数 ≥4：小区吞吐**几乎不变**（±0.3%）
- UE 数 1~2：小区吞吐大幅上升（+83%~+259%）
- MU 场景：`mu_share` 下降、`mu_pair_rejects` 上升（机制见上），但小区吞吐仍更高
- 新增 `harq_max_processes`、`harq_ues_with_inflight_tb_at_end` 两个 cell 键
- `harq_feedback_wait_skips` 在进程够用时降到 0

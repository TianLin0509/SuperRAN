**分支 / SHA**：`feat/harq-multiprocess-20260904` / `<提交后回填>`　**风险档**：红

## 改了什么物理机制

`experience_v2` 唯一系统主循环的 HARQ 进程模型。改前每个 UE 只有一个槽位，
发出一个 TB 后要等 ACK/NACK 回来才能发下一个；`DDDSU` 下逐相位要等 2~6 个 TTI。
full_buffer 与 ftp3/mixed 只是同一路径的不同话务工作点，不再各有一份实现。

改后每个 UE 有 `SystemConfig.harq_max_processes` 个进程
（默认 **8**；38.213 §5.3 下行上限 16；设成 1 精确退回旧行为）：

- `harq_inflight: dict[ue, dict[harq_id, TB]]` + 每 UE 一个有序空闲 id 池
- 发新传时从池里取最小的空闲 id；ACK 归还；NACK 不归还，状态转 `retx_ready`
- 反馈处理**遍历该 UE 的每个在途 TB**——`DDDSU` 下 t0..t3 发出的 4 个 TB 会在
  t5 同时到期，一个都不能漏
- 候选筛选从 `u not in harq_pending` 改为「有空闲进程能发新传 **或** 有同类型
  时隙的重传就绪」
- 重传优先与「重传只能回同类型时隙、MCS/rank/TBS 冻结」的规则原样保留

## 为什么

单进程让 UE 在等自己反馈的时候完全发不出东西。它不是"待补的半成品"里那种
无害简化——`DDDSU` 下一个 UE 每发一个 TB 就要停 2~6 个 TTI。

## 证据

### `max_processes=1` 精确退回旧行为

在 #25 统一路径之后，使用同一树、同一夹具对 `origin/develop` 的单进程实现与本分支
`harq_max_processes=1` 做归一化结果指纹比较；新增元数据键之外逐值一致。脚本内还钉住
DDDSU 的 t0/t5 单进程时序、终次反馈与 1/2/4/8/16 进程单调关系。

### 当前收益形状：体验速率显著变化，小区吞吐接近 offered-limited

当前 4 UE / ftp3 受控夹具（同链路表、同随机流）实测：

| 指标 | 1 进程 | 8 进程 |
|---|---:|---:|
| 体验速率中位 | 112.2 Mbps | **349.8 Mbps** |
| 完成时延 p50 | 39.2 ms | **12.0 ms** |
| 小区吞吐 | 67.2 Mbps | 68.4 Mbps |
| `harq_feedback_wait_skips` | 1975 | **0** |

有限话务小区吞吐接近 offered-limited：被挡住的 UE 会由别的 UE 顶上；真正被单进程
压住的是单个文件的完成时间。该夹具证明机制方向，不是现场收益承诺。

### DDDSU 下 4 个进程就够

已调度 TTI 数随进程数：`{1: 2, 2: 4, 4: 8, 8: 8, 16: 8}`（10 个 TTI 的最小夹具）。
默认 8 是留余量，不是必需。

## 2026-09-04 内网审核后的修改

内网 Agent 对本 PR 给出 **REVISE**，一条必改。两条都已修，并各带棘轮。

### 修 1：多进程必须建立在发送时扣 buffer 的唯一队列口径上（审核报告 4609d9d）

审核指出：多进程若仍按 ACK 扣 buffer，会让同一批字节被另一个进程再次组成新 TB。
**属实**。#25 已删除当时漏修的 legacy capacity `_Traffic`，当前只有
`experience.DrbQueue` 一份队列实现，继续采用 #21 的“首传发送即扣、重传只占资源”。

原 capacity 专用测试已迁到唯一系统路径：1/8 进程有限话务均满足发送字节不超过到达
字节；首传全错时，重传全对与全丢的发送吞吐逐值相同，差别只进 `residual_bler`。

### 修 2：`acked_goodput` 恢复「NACK 给 0」的合同（审核报告 dac4ede 问题 2）

审核指出 PF 的 `r_avg` 改用含 NACK 首传的字节更新，坏链路用户可能被死亡螺旋。

**一半属实。** 默认口径 `auto`（= `scheduled_tbs`）用的是 `tb_bytes`，本来就与 ACK
无关，**改动前后都没变**，审核那句「改前用 acked」对默认路径不成立。但
`pf_accounting="acked_goodput"` 确实被改坏了：`SchedulerConfig` 的注释白纸黑字写着
这个口径「NACK 时给 0」，而 buffer 改成发送时扣减后 `sent` 在 NACK 时也是正数。
已改回 `credit = sent if ack else 0`。原提交没有真正约束这条分支；当前新增 allocation
级棘轮，直接断言 ACK 的 `pf_credit_bytes=payload_bytes>0`、NACK 的 credit=0。

## 没证明什么

- **发送时扣 buffer 的历史 bug 量级没有重新量化成现场 KPI。** 当前证明的是守恒与
  对错不回扣，不是现场偏差百分比。
- **`acked_goodput` 只验证了 ACK/NACK 两端点。** 默认 `scheduled_tbs` 另有既有棘轮；
  `legacy_fullband` 是明确反向控制，没有重新做性能判决。
- **依赖前一个 PR 的记账口径。** experience 侧的多进程必须建立在"buffer 在发送时
  扣减"之上：按 ACK 扣减时，被 NACK 的 TB 其字节仍留在队列里，同一个 UE 的另一个
  进程会把同一批字节再发一遍，原 TB 的重传随后就会硬失败。这条依赖是实测撞出来的，
  不是设计时想到的。
- **没有验证 MU 配对下的多进程重传**。`_build_mu_plan` 走另一条路径；有重传就绪时
  MU 本来就被禁用，但没有为"多个进程同时就绪 + MU"写针对性用例。
- **没有建模 RV 序列**（RV0/RV2/RV3 轮转），按任务书要求不做。
- **没有改 K1 时序**。当前取的是"第一个可用上行机会"，即**最小 K1**，
  与 38.213 §5.3 Table 9.2-7 的查表值有差距——真实 K1 只会更大，
  所以本模型的反馈比现场快、OLLA 收敛也偏快。已在 `amc_policy` 与 CLAUDE.md
  写明。
- **没有量化多进程对 OLLA 稳态的影响**。已观察到一个真实交互：进程放开后
  UE 发得出 3 倍的 TB，MU OLLA 收到的反馈也多 3 倍、偏置爬得更高，实发 MCS
  的预测 BLER 更容易越过 0.5 的配对准入线，于是 MU 占比从 0.379 掉到 0.160、
  配对拒绝记录从 95 涨到 735。**这不是 bug**（已由 17.2d 显式钉住），
  但"OLLA 步长是否要随进程数重新标定"没有做统计判决。
- 没有测 `max_processes` 与 CSI 老化、SRS 跳频的交叉场景。
- 进程数上限 16 是按 38.213 §5.3 写的，**没有验证** 16 进程下的内存/耗时代价。

## 影响哪些 KPI

- 当前 4 UE / ftp3 夹具：体验中位 112.2→349.8 Mbps、完成 p50 39.2→12.0 ms
- 同一夹具小区吞吐 67.2→68.4 Mbps；不能外推为所有负载下都不变
- MU 场景：`mu_share` 下降、配对拒绝记录上升（机制见上），但小区吞吐仍更高
- 新增 `harq_max_processes`、`harq_ues_with_inflight_tb_at_end` 两个 cell 键
- `harq_feedback_wait_skips` 在进程够用时降到 0

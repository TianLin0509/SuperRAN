# 2026-09-04 CSI/AMC — CQI 链路改为运行时按 SRS 周期事件触发

**分支 / SHA**：`feat/cqi-event-driven-20260904` / `<提交后回填>`　**风险档**：红
**报告**：`C:\VibeData\Artifacts\Reports\SuperRAN\20260904-cqi-event-driven.html`

## 改了什么物理机制

**MCS 决策输入 `sinr_tx_db` 的产生时刻**。

改前：整条 CQI 链（PMI-SINR → 4-bit 量化 → IIR → 反查目标 BLER 的 SINR 门限
→ 加 BF Gain）在 `build_link_tables` 里一次性按信道快照算完，主循环直接查
`tables[u].sinr_tx_db[snap, rank-1]`。

改后：新增 `amc_policy.CqiReporter` / `CqiReportConfig`
（`SystemConfig.cqi_report`，默认 `cqi_period_tti=None`、`csi_delay_tti=3`、
`ue_implementation_loss_db=1.5`）。两条主循环每个 TTI 驱动一次上报：

- 每个上报周期上报一次；两次之间 CQI 保持不变。**周期跟 CSI 报告周期
  （`CsiConfig.csi_report_period_ms`，默认 20 ms = 40 TTI），不跟上行 SRS 周期**
  ——用户 2026-09-04 定。SRS 是上行探测、服务于互易性预编码；CQI 来自
  CSI-RS + CSI 报告。`cqi_period_tti` 给整数只用于消融
- UE 测的是 `tti − 上报周期 − csi_delay_tti` 时刻的信道
- 测到的 PMI-SINR 先扣 `ue_implementation_loss_db`（本振噪声 + 解调实现损失
  的等效惩罚），再量化、再进 IIR
- **BF Gain 不进上报状态**——它是瞬时量，基站读的时候按**当前快照**加回去

`CqiReportConfig(enabled=False)` 退回建表阶段那份预计算，**逐位一致**。

### 实现方式：回写，不是逐点改读

两条主循环加起来有二十多处读 `sinr_tx_db` / `sinr_tx_rbg_db`（频选打分、
MU 准入、rank 观测、grant 复算……）。逐点改成调函数等于二十多个可能漏掉的
地方，而漏掉的那个会**静默**继续用建表阶段那份值。

所以 `attach_runtime_cqi()` 给每次仿真造一份**私有的**链路表副本（只复制这
两个数组），reporter 每次上报后把结果回写进副本的当前快照那一格。读侧一行
没改。私有副本是必须的：同一份链路表会被多次 replication 复用，原地改会让第
2 次开始的重复实验带着第 1 次的 CQI 状态跑。

## 为什么

离线预计算的 AMC 坐标**系统性乐观**，而且它的时间栅格是信道快照（默认 5 ms），
表达不了 2 ms 的 SRS 周期；也没有 SRS 处理时延和 UE 实现损失这两项。

## 2026-09-04 补：与主线 #23 合流，门限必须走表相关的那个入口

迁到含 #23（BLER/EESM 显式化）的新主线时，`test_system` 崩在
`ValueError: MCS must be 0..27, got 28`。

原因：本 PR 的 `_cqi_quantiser` 缓存了**两份**数组——量化用的 `edges` 走
`la._internal_cqi_thresholds`，反查发送门限用的 `rows` 却自己去
`bler_curves.get_curve` 按预置曲线另算了一份。

**`bc.get_curve` 是表无关的**：它只按 MCS 序号取预置曲线，那批曲线就是 table 3
的。而 `la._internal_cqi_thresholds` 对 table 1/2 走的是**解析 BLER 模型**
（`make_bler_model(table).required_sinr_db(MCS_TABLES[table][mcs], 20000, target)`），
只有 table 3 才回落到预置曲线。#23 把 table 1/2 的解析模型和用例加进主线，
于是这条一直存在的岔路第一次被走到。

两张表的表现不一样，因为内部 CQI → MCS 的**序号**映射 table 2 与 table 3 相同
（都止于 MCS27）、table 1 不同（止于 MCS28）：

| mcs_table | 旧的 get_curve 路径 | 后果 |
|---|---|---|
| 3（默认） | 与表相关入口**逐值相同** | 本 PR 所有既有结论不变 |
| 1 | 最高行请求 MCS28，预置曲线只到 MCS27 | 直接抛 `ValueError: MCS must be 0..27, got 28`——这就是崩溃点 |
| 2 | 序号映射与 table 3 重合，于是**静默拿到 table 3 的门限** | 15 行**全部**偏，最大 3.29 dB。不崩，错得无声 |

所以这不只是修一个崩溃：table 2 下旧写法把 QAM64 表的 AMC 门限当成了 QAM256 表的。

改法：这两份数组本来就该是**同一份**——量化是"有多少个门限 ≤ 观测值"，反查是
"同一组门限按行下标取值"，同一组门限的两个方向。#23 也已经把
`system._cqi_threshold_sinr` 改成 `la._internal_cqi_thresholds(target, table)[cqi_index]`。
`_cqi_quantiser` 现在只返回这一份，量化与反查共用，`bler_curves` 的依赖一并删掉：
运行时 CQI 只经 `linkadapt` 一个入口拿门限，与离线路径同源。

三张表 × 两个目标 BLER 都已核对：门限单调不减（`searchsorted` 的前提），
且量化结果与 `la.select_reported_cqi` 在 200 个探测点上逐值等价。

## 一个来自内网审核的连带发现：本 PR 顺手缓解了上一层的饿死

内网审核对上一个 PR（HARQ 多进程）的 问题 2 指出：放开进程后 24 UE 饱和小区里
最弱那个（geo SINR −0.74 dB）会 served = 0，且饿死兜底阈值扫 200/100/50/20/10 ms
都消灭不了。

**叠加本 PR 之后那个饿死消失了。** 运行时 CQI 让 AMC 变保守，强用户不再一口吃满，
最弱 UE 从 0 回到 0.499 Mbps（单进程对照 0.496 Mbps）。留下的只是公平性下降：

| | 1 进程 | 8 进程 |
|---|---|---|
| 饿死数 | 0 | **0**（在只到多进程那一层时是 1） |
| 最弱 UE | 0.496 Mbps | 0.499 Mbps |
| p5 | 0.616 Mbps | 0.499 Mbps |
| Jain | 0.4552 | 0.4281 |
| 小区吞吐 | 242.3 Mbps | 243.1 Mbps |

`test_multiprocess_harq_weakens_the_starvation_guard` 的断言随之从"会饿死"改成
"公平性下降"——**断言的是留下来的那个机制，不是被上层掩盖掉的症状**。
饿死会不会在别的场景回来取决于 AMC 工作点，做公平性结论前要在目标场景自己确认。

## 没证明什么

- **上报周期的口径已按用户 2026-09-04 的裁决改为跟 CSI 报告周期**（任务书原本
  写的是跟上行 SRS 周期，那会让 CQI 比配置的 CSI 报告周期新鲜 10 倍）。
  但 `csi_report_period_ms=20 ms` 这个值本身**没有被验证**是现场值。
- **IIR 的 λ 是"每次上报"作用一次，不是"每毫秒"。** 拉长 SRS 周期同时拉长
  了滤波器在时间上的记忆：周期 40 TTI 时 AMC 实测**更保守**（BLER 0.028），
  与任务书"CQI 陈旧 → MCS 偏激进 → BLER 略高于 target"的预期**相反**。
  要让 λ 表示固定时间常数需要按周期比例换算，**本次没有做**。
- **1.5 dB 的 UE 实现损失只保证方向，不保证落点。** 它一定让 AMC 更保守；
  是否"正好把陈旧带来的激进补回目标"依赖场景落在 MCS 量化台阶的哪一侧
  ——一个夹具落回 0.096（贴着目标），另一个过冲到 0.027。**未经现场设备
  数据标定**，不能当现场值报出去。
- **`outage` 仍是建表阶段按预计算 CQI 判的**，没有跟着运行时上报走。
  这意味着"上报 CQI0 → 不调度"的判据用的是离线那份 CQI，与运行时的
  `reported_cqi` 可能不一致。**本次没有改，也没有量化这个不一致有多大。**
- **`mcs_tx` / `cqi_index_per_snapshot` 等建表阶段的诊断数组没有跟着更新**，
  它们保留建表口径，只作来源审计。
- 没有建非周期 CQI（aperiodic CSI request），按任务书要求不做。
- 没有改 PMI 权计算与 rank 选择逻辑。
- 没有做多 replication / 多种子的统计判决；上面所有数字都是单次运行。

## 影响哪些 KPI

**默认口径下全面变化**：AMC 坐标比离线保守约一档，首传 MCS 下降、吞吐下降、
首传 BLER 从系统性偏高（0.32~0.44）回到目标附近。PRB 利用率上升
（同样话务下 EDF 的 30% 工作点变成 40%）。

**OLLA 会顶到默认钳位**：`olla_max_db=3.0` 在部分场景下不够用了。
做 OLLA 稳态实验前先确认两臂都没顶到钳位。

新增 `cqi_update_count_mean` / `cqi_age_tti_max` 两个 cell 键，
以及 `diagnostics["cqi_report"]` 的逐 UE 明细。

**改前的所有 AMC / 吞吐结论都不能与改后的数字放进同一张趋势图。**

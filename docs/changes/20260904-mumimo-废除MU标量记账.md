# 2026-09-04 MU-MIMO — 废除 se_ratio_legacy 标量记账，只保留 pair 表

**分支 / SHA**：`feat/mu-drop-legacy-se-ratio-20260904` / `<提交后回填>`　**风险档**：红
**报告**：`C:\VibeData\Artifacts\Reports\SuperRAN\20260904-mu-drop-legacy.html`

## 改了什么物理机制

capacity 主循环里 MU 配对的**代价怎么记账**。删掉 `mu_accounting="se_ratio_legacy"`
这条路径，以及为它服务的标量入口 `simulate(..., mu_se_ratio=)`、
`simulate_replications(..., mu_se_ratio=)`、`calibrate_traffic_to_prb(..., mu_se_ratio=)`
和 worker 进程里的对应字段。现在唯一的 MU 口径是 `pair_table`：
MCS 从 pair 表的 `CorrLoss + PowerLoss` 平移出来、TBS 按该 MCS 全带算、
误块抽签用 pair 的真实 SINR。

选中被删的口径不再静默退回，而是在 `SchedulerConfig.__post_init__` 直接报错。
MU 开着却没有 pair 表时，主循环的配对分支也从"按标量决定"改成硬失败。

## 为什么

标量口径把配对的代价只表现为 `TBS × mu_se_ratio / K`，MCS 决策与误块抽签都还走
SU 单用户口径——也就是"**包变小，但一点也不更容易错**"。物理上说不通：配对后
每流只分到 P/K 的功率、还要吃对方的残余干扰，同一档 MCS 的误块概率本来就更高。
配对越激进，这个口径给出的结果越乐观。

对照 AirView 的 `GDlMuMimoScheduler::calcPairSinr` / `calcPairCQI`：功率损失与层间
干扰都在配对后的 SINR 里，MCS 也用配对后 SINR 选。SuperRAN 的 pair 表路径与它
在主要环节上一致（功率损失显式记为 `-10log10(2)`、相关性损失记为
`pred_SINR - SU_pred - power_loss`，逐 RBG 也有）；只有 legacy 那条对不上。

保留成"兜底"没有价值：它唯一的作用是让这种乐观**静默**发生。

## 证据

- `SchedulerConfig(mu_enabled=True, mu_accounting="se_ratio_legacy")` 在构造时抛
  `ValueError`，错误信息点名 `pair_table` 与 `build_link_tables(..., mu_enabled=True)`。
  用例见 `tests/test_system.py` 第 3 节。
- `inspect.signature` 断言 `simulate` / `simulate_replications` /
  `calibrate_traffic_to_prb` 都不再接受 `mu_se_ratio`。
- 开了 MU 但链路表没有 pair 数据时硬失败，错误指向 `build_link_tables`。
- pair 表路径**一行没动**，KPI 与改前一致：test_system / test_physics_invariants /
  test_csi_aging / test_rng / test_e2e / test_mumimo（`__main__` 入口，退出码 0）；
  test_scheduler_p0 14 passed、test_carrier 33 passed、test_mcp_server 1 passed、
  test_system_sim_tool 15 passed。
- ruff 回到 `develop` 上原有的 2 处告警（删除后新暴露的两个未使用局部变量
  `mu_load_rng`、`n_pair` 已一并清掉）。

## 没证明什么

- **没有重新验证 pair 表路径本身的物理正确性**。本次只删另一条路径；pair 表的
  `CorrLoss`/`PowerLoss` 拆分、准入判据、逐 RBG 损失都按原样保留，未做新的对照实验。
- **没有量化"以前用 legacy 跑出来的历史结果偏乐观多少"**。仓库里原有的对照
  （同一组配置：pair 表把首传平均 MCS 从 23.48 压到 19.93，legacy 是 22.68→22.69）
  是删除前的记录，本次没有重跑。
- `measure_mu_gain()` 保留为独立的**测量**入口（test_csi_aging 用它比较不同 CSI
  老化下的 MU/SU 聚合比），但它的返回值不再进任何仿真路径——**没有验证**
  它作为纯测量工具的数值口径是否仍然是使用者想要的那个。
- 删除只覆盖了 `src/`、`tests/`、`scripts/run_dl_amc_chain_audit.py` 与文档；
  历史结果 JSON 里遗留的 `mu_se_ratio` 字段没有清理，也不打算清理。

## 影响哪些 KPI

默认路径（`mu_accounting="pair_table"`）**零变化**——它一行没动。
只用被删口径跑过的旧配置现在会直接报错而不是出数。
`SystemResult.cell` 少了 `mu_se_ratio` 键，`mu_pair_graph.reason` 不再有
`se_ratio_legacy` 取值。

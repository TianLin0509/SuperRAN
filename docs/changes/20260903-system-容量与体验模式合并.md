## 改了什么物理机制

**系统级仿真从两条评估路径变成一条。** `evaluation_mode` 开关整个删除，
`system.simulate()` 恒走 `experience.simulate_experience()`。

过去所说的"容量模式"现在是**同一条路径上的一个话务配置点**：
`TrafficConfig(model="full_buffer")`。物理因果链是：

1. **队列无限** → `_build_su_plan` 的"按 TBS 反查最小够用 RBG"结果恒等于
   "全部可用 RBG"。按需分配自动退化成全带宽分配。
2. **全带宽分配** → **RBG 全部用满**（`resource_utilization = 1.000`）。
   **纠正**：早先这里写"每个忙 TTI 恰好一个 SU"，那只在**频选关 + MU 关**时成立
   （实测 1.0000），是退化解不是普遍规律。出厂默认（频选 auto）实测 **1.0942**，
   开 MU 是 **1.7418**——频选会把带宽按 RBG 切给多个用户，MU 本来就配对两个。
   两者都是正确的物理行为，2×2 实测表见 `CLAUDE.md` 与第 8 节棘轮。
3. **解调 SINR 照旧按本次实际授予的那几个 RBG 聚合**——满缓冲下"那几个"天然
   就是全部，所以不需要、也没有为它开任何特例分支。
4. **代价**：DRB busy period 永不结束，因此**所有需要 burst 真的传完的键返回
   `None`**——包括 TS 28.552 的标准吞吐本身（`drb_throughput_rel19_mbps` /
   `cell_experienced_mbps`，样本只在 buffer 排空事件上形成），以及
   `cell_experienced_completed_only_mbps`、`cell_head_inclusive_experienced_mbps`、
   完成时延分位数、`pdb_miss_ratio`。满缓冲要看的是工程口径，见下一节。

## 体验速率：标准与工程两套口径，满缓冲下只有工程口径有值

**这一节记录本次改动中被纠正过三次的说法，三次都记在这里，不遮。**

1. 我先说"体验速率在 full_buffer 下按定义无定义"。**错。** 维护者指出后补上了
   ITU-R M.2412 / TR 38.913 口径（`ue_served_*`），它在满缓冲下不但有值，而且
   正是满缓冲评估的主指标。
2. 我改成"只有 28.552 busy-period 口径无定义"。**还是错在关键处。** 维护者
   第二次追问"掐头去尾的业务量 ÷ 掐头去尾的时间，为什么算不出来"——**这个数确实
   算得出来**，而且顺手查出实现里有个真 bug：在飞的 busy period 从不进统计，
   这是普遍的右删失，普通有限话务过载下同样中招。
3. 我于是把在飞段直接混进了 `drb_throughput_rel19_mbps`。**外部审核判这是口径
   错误，接受。** TS 28.552 的样本只在 "DRB DL buffer emptied" 事件上形成
   （TS 128 552 V19.5.0 p54），buffer 没排空就没有样本；那个数算得出来不代表
   它是 28.552 的数。

**最终形态**：算得出来的那个数照报，但另起字段
（`active_window_goodput_mbps`，`kind = "engineering_active_window"`，名字里不含
`rel19`），标准字段在满缓冲下如实报 `None`。

| 口径 | 键 | 分母 | full_buffer 下 |
|---|---|---|---|
| ITU-R M.2412 / TR 38.913 | `ue_served_p5_mbps` / `_median_` / `_mean_` | 观测窗长 | 有值，5% 分位即 cell-edge user throughput |
| TS 28.552 busy-period（**标准**） | `cell_experienced_mbps` / `drb_throughput_rel19_mbps` | 已排空的 busy period：首传 → 清空 buffer 前一段首传发送 | **报 `None`**（样本不形成） |
| 在飞窗内段（**工程**，非标准） | `active_window_goodput_mbps` | 在飞 busy period 落在窗内那段 | **有值**；满缓冲下因分母趋同而接近 ITU 口径，但分子同源 |

**为什么在飞段不能按标准口径处理。** 标准样本只在 buffer-emptied 事件上形成，
并排除清空 buffer 的最后一个发送 piece；在飞 busy period 尚未发生这个事件，
也就不知道哪一段最终会成为要排除的尾段。工程窗内段因此必须另起字段，不能冒充标准样本。

**但在飞段仍然要报**，因为右删失是真的：只数已排空的 busy period 会把"慢到没
传完"的 burst 系统性丢掉。**偏差方向不固定**——实测既见过偏乐观（11.59 → 含在飞
8.78），也见过偏悲观（126.0 → 131.9）。所以它另起字段
（`throughput_kind = "engineering_active_window"`，名字里不含 `rel19`），
按发送净荷速率定义（发送净荷字节 ÷ 经过时间），永不进标准字段。

**卡住它的是一个普遍的右删失，不是 full_buffer 特有的。** 实现里只统计
`q.done`（已排空的 busy period），在飞的 `q.active` 从来不进统计。于是任何在
仿真结束时还没传完的 burst 都被整条丢掉——而慢 burst 更容易没传完。这和
`arrival_item_metrics` 里仓库自己已经诊断并修过的那个删失是同一个 bug
（原注释：*"旧实现要求 completion_tti 也存在，会把'已经开始发送、但在仿真结束时
尚未传完'的长等待对象删掉，过载算法反而更容易留下漂亮样本"*）。

实测这个删失在**普通有限话务**下就在咬人（8 UE / DDDD / 1 s）。下表“工程窗内段”
是第一次修复得到的值；最终实现把它从标准字段拆出，命名为
`active_window_goodput_mbps`，标准字段在没有 buffer-emptied 事件时仍为 `None`：

| 场景 | completed-only | 工程窗内段 | 完成/在飞 |
|---|---|---|---|
| 轻载 ftp3 5 Hz × 50 kB | 47.87 | 47.87 | 36/0（**零扰动**） |
| 中载 ftp3 5 Hz × 500 kB | 11.59 | 8.78 | 1/8（旧值拿 9 个里唯一传完的 1 个算的，高 32%） |
| 重载 ftp3 20 Hz × 500 kB | **None** | 7.23 | 0/8 |
| full_buffer | **None** | 7.05 | 0/8 |

**重载那一行是关键**：旧代码在一个普通的有限话务过载场景下就已经返回 `None`。
full_buffer 从来不特殊，它只是"每个 busy period 都在飞"的极端情形。

满缓冲下 UE 一直活跃，"在传时多快"与"全窗平均多快"的分母趋同——实测
`active_window_goodput_mbps = 7.05` vs `ue_served_mean_mbps = 7.03`，差 0.3%。
但两者的发送字节分子同源，这个接近只检查分母边界，不是字节记账的独立自证。

**偏差方向不是不变量。** 慢 burst 更不易传完会让 completed-only 偏乐观（中载
那档 11.59 vs 8.78）；但若在飞的恰好是刚起步的好信道用户，方向就反过来（手工
构造表那组 125.98 vs 131.91）。棘轮只守"含不含在飞样本会改变结果"，不守方向。
样本构成由 `drb_throughput_completed_bursts` / `_inflight_bursts` /
`_inflight_share` 如实上报。

`ue_served_*` 是 `users[].served_mbps` 的跨 UE 分布，**无条件计算、不按话务模型
分支**；在飞 busy period 的统计同理，对所有话务模型一视同仁。两者都不构成
"为 full_buffer 开特例"。

两个口径仍然**不是同一个数的两种精度**：轻载 FTP3 实测 `ue_served_mean_mbps=1.85`
vs `cell_experienced_mbps=46.96`，差 25 倍（UE 全时段平均 vs 它的 burst 在飞时的
速率）；只有满缓冲下分母才趋同，所以数值接近，但不能拿来互相验证分子。

同时把三组本不属于容量语义、只是历史上恰好只在容量分支实现过的诊断补进唯一
路径：IoT 分布（`iot_db_median/p5/p95`、逐样本与逐用户两个有效率、
`high_iot_ue_share`）、`edge_mcs_p5`、`olla_target_bler`，以及对应的三条告警
notes（IoT 逐样本有效率、边缘 MCS 偏高、全程覆盖外用户）。它们是链路表的纯
函数，和话务模型无关。

### 一、「两个速率口径互相印证」是假的自查 —— 撤回

我把 `ue_served_mean` 与 `active_window_goodput` 吻合到 0.16% 当成合并正确的主要

**它们的分子是同一份发送净荷记账**：`tr.transmit()` 返回的那个 `payload`，
一边累进 `served_measured`（喂 ITU 口径），一边塞进 `TxEvent`（喂在飞段速率）。

处理：全部改成如实说明「这验的是分母重合，不验净荷记账」，并写清**真正能抓记账

## 为什么

1. **两条路径是重复实现，必然漂。** 历史上 MU 记账、HARQ 反馈时序、rank 策略
   都出现过"在一条路径上修好、另一条还留着旧行为"，`amc_policy.py` 这个共享
   模块就是为了堵这个漏洞才建的。删掉一条从根上解决。
2. **容量分支在它自己的招牌场景下是坏的。** `sys_capacity_full_buffer` 跑出来
   `accounting_error_pct = 3.7e21`（满缓冲投 `1<<62` 字节进 backlog 却不计入
   `offered_bytes`），而仓库自己的规矩写着"差 >1% 就是 bug 不是现象"。
   合并后同场景是 `0.0`。
3. **容量分支报的体验速率是 0，那是在假装"测到了 0 Mbps"。** 现在 busy-period
   口径报 `None` 并在 notes 里说明为什么没有边界，同时把真正适用于满缓冲的
   ITU 口径（`ue_served_p5_mbps`）补上——旧路径两个都没有。

关键数字（8 UE / 17 RBG / DDDD / 2 s / 合成瑞利信道，开 OLLA）：

|---|---|---|

**吞吐差已按仓库统计合同重测（CRN + Gate 3 + Wilcoxon）。** 两臂用同一组链路表
（`build_link_tables` 未被本 PR 改动，指纹逐位一致）、同一 `master_seed` 与同一
replication 序列；legacy 臂在 `origin/develop` 的 worktree 上跑，单路径臂在本分支跑。

指标是 `cell_served_mbps`（Mbps）。**方向统一取「单路径 − legacy」**，
负号 = 单路径更低；CI 也按同一方向给，单位 Mbps。

| 对照 | legacy | 单路径 | 差值 | 差值 95% CI | 判决 |
|---|---|---|---|---|---|
| 默认（频选 auto，OLLA 关） | 54.750 | 52.957 | −1.79（**−3.27%**） | [−1.968, −1.618] | Wilcoxon p=0.0078，门 3 通过 |
| 像对像（都用宽带 `fs=off`，OLLA 关） | 54.750 | 54.440 | −0.31（**−0.57%**） | [−0.450, −0.170] | Wilcoxon p=0.0078，门 3 通过 |
| **现实默认（频选 auto，OLLA 开）** | 56.003 | 56.150 | +0.15（**+0.26%**） | [+0.055, +0.239] | Wilcoxon p=0.0156，门 3 通过 |

> **这张表上一版三个符号全是反的**（写成 +3.27 / +0.57 / −0.26），因为当时用的是
> 「legacy 比单路径高多少」这个未标注的约定，与列的排序读起来正好相反；CI 的单位
> （Mbps）也没标。数值本身没错。本轮从保存的逐 replication 数据重算并统一方向。

**方向随配置翻转，不存在一个"系统性平移"的单一数字**（本 PR 早先的
"约 0.6% 系统性偏低"是错的，那个数只在「都关 OLLA + 都用宽带」这一种非默认
配置下成立）：
* 开 OLLA（**默认**）时单路径反而略高 0.26%；
* 只有关掉 OLLA 才看得到口径差，且频选打开时单路径低 3.27%——那是
  「授予子带 dB 均值高估有效 SINR」在没有外环补偿时的表现（同配置首传 BLER
  0.101 → 0.179）。开 OLLA 后外环把它压回去。

**B05 基准（PF vs max-C/I，满缓冲，8 次重复 + CRN）两条判据都仍成立**：
max-C/I 吞吐 66.34 vs PF 52.76 Mbps，95% CI [+13.26, +13.91]，significant；
PF 的 Jain 0.916 vs max-C/I 0.427，95% CI [+0.483, +0.495]，significant。
效应量比旧路径小（旧路径吞吐差约 +18.5 Mbps），物理结论不变。

棘轮测试（把容量分支恢复回去就会红）——`tests/test_physics_invariants.py`：

1. `full_buffer` 走的就是体验路径，`model_version` 恒为 `experience_v2`
2. 满缓冲下 `scheduled_ues_per_busy_tti == 1.0`
3. 满缓冲下 `resource_utilization == 1.0`
4. `cell_experienced_mbps` / `drb_throughput_rel19_mbps` 报 `None` 而不是 0
5. `cell_served_mbps > 0`
6. **full_buffer 下 `ue_served_mean/median/p5_mbps` 有限且为正**——满缓冲评估的
   主指标不许消失（把它们也置 `None` 就会红，已实际注入验证）
7. `ue_served_p5 <= ue_served_median`；三个统计量来自同一分布
8. `sum(users[].served_mbps) == cell_served_mbps`（用户级与小区级同源）
9. 几何最好的 UE 拿到的用户吞吐高于最差的（PF 不抹平几何差异）
10. 有限话务下两个口径同时有值，且 `ue_served_mean < cell_experienced`
    ——证明它们是两个定义，不可互换

## 没证明什么

- **原有 9 个系统级 preset 的 `expect` 锚点作废后仍未恢复。** 数值已删除（不是留
  着打标签——`test_sysscenes.py` 的规矩是 `measured: false` 就不许有数值锚点）。
  本次新造了 5 个实测锚点顶上（3 个单小区 + 中心站 + 边缘站对照组），
  `test_sysscenes.py` 124 通过 / 0 失败。**但那 9 个旧场景要恢复，还得按标准密度
  分别重新生成各自的数据集，本轮没做。**
  当初卡住它们的阻塞已经解开：`sr_system_sim(serving_cell=...)` 是本次新增的。
- 所有对照实验用的是合成瑞利信道、无 CSI 老化、rank2 上限、DDDD/DDDSU。
  开 CSI 老化、开 SRS、上 64 端口后这几个口径差会不会放大，**没测**。
- **开 MU（pair_table）后两条路径的差异没有单独量化**。SU 侧测了。
- **合并 #23 之后没有重跑 CRN + Gate 3 的三组吞吐对照。** 四个锚点 69 项逐字未变
  是重跑的强前提，但不等于重跑过——对照的 legacy 臂在旧 worktree 上，重建要再跑
  一遍全套。
- **边缘站对照组的 BLER 是 0.32× 目标，按本仓库的判据它不合格**，因此只能当反向
  对照，不能当"另一个多小区锚点"。原因已定位到 MCS 撞表 3 天花板（见下），
  但**没有去构造一个"信道好但外环仍有余量"的多小区锚点**。
- `bimodal` → `cdf` 的迁移用的是**机械转写**：
  `scripts/make_field_bimodal_cdf.py` 把退役的三个 RBG 数概率旋钮按 legacy
  那个写死的 3.0 bit/s/Hz 折算成包长 CDF。**这不是新的现网测量**，只是让
  `sys_field_bimodal_traffic` 这个场景不随 legacy 路径一起消失。
  口径本身变了：现在一次传输占几个 RBG 由真实 TBS 反查决定。
- 运行时间没有做优化。满缓冲工况下体验路径比旧容量分支慢 19~48 倍
  （2 s 仿真：0.15 s → 2.89 s（关频选）/ 7.26 s（开频选））。
  **"满缓冲下频选搜索挑不出东西，跳过它"这条优化被明确否决**——那会重新造出
  一条只在特定话务下成立的路径。这是已知代价，不是遗漏。

## 选哪个小区：从"数据集层的 12 dB"到实测的容量差

上一版只能给数据集层的几何 SIR 差（中心站 4.22 dB vs 边缘站 16.25 dB），仿真臂
三次被系统按内存杀。本轮用 `replication_workers=1` 串行跑通了，两臂**只差一个
`serving_cell`、其余逐字相同**（`test_sysscenes` 的 `pair_with` / `pair_varies`
机制强制受控）：

| | 中心站（小区 1，13 UE） | 边缘站（小区 11，9 UE） | 差 |
|---|---|---|---|
| 几何 SIR 中位 | 4.22 dB | 16.25 dB | 12.0 dB |
| `iot_db_median` | 23.23 dB | 16.78 dB | 低估 6.45 dB |
| `cell_served_mbps` | 620.52 | 799.31 | **高估 28.8%** |
| `ue_served_p5_mbps` | 28.24 | 71.67 | **高估 154%** |
| `avg_mcs_first_tx` | 21.88 | 26.19 | |
| `olla_db_mean` | −3.07 dB | **+1.43 dB** | |
| `bler_first_tx` | 0.1041（1.04×） | 0.0315（**0.32×**） | |

**边缘站那一列同时是"场景合格判据"的反面教材。** 它的 `avg_mcs_first_tx` 26.19
已经贴着 MCS 表 3 的最高档 27，`olla_db_mean` 为正说明外环还想往上推却推不动；
MCS 撞天花板 ⇒ 外环失去调节余量 ⇒ BLER 只能低于目标。所以 0.32× 不是随机偏差，
是**信道太好导致的结构性结果**——这条也解释了为什么锚点必须挑被邻区包围最完整
的小区。

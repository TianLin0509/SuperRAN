## 改了什么物理机制

**系统级仿真从两条评估路径变成一条。** `evaluation_mode` 开关整个删除，
`system.simulate()` 恒走 `experience.simulate_experience()`。

过去所说的"容量模式"现在是**同一条路径上的一个话务配置点**：
`TrafficConfig(model="full_buffer")`。物理因果链是：

1. **队列无限** → `_build_su_plan` 的"按 TBS 反查最小够用 RBG"结果恒等于
   "全部可用 RBG"。按需分配自动退化成全带宽分配。
2. **全带宽分配** → 每个忙 TTI 恰好一个 SU（或一对 MU）。实测
   `scheduled_ues_per_busy_tti = 1.000`、`resource_utilization = 1.000`。
   这正是历史容量分支硬编码的行为，现在它是分配逻辑的退化解而不是另一套代码。
3. **解调 SINR 照旧按本次实际授予的那几个 RBG 聚合**——满缓冲下"那几个"天然
   就是全部，所以不需要、也没有为它开任何特例分支。
4. **代价**：DRB busy period（buffer 空→非空→空）永不结束，TS 28.552 的
   **busy-period 吞吐**因此无边界可用。`cell_experienced_mbps` /
   `drb_throughput_rel19_mbps` / 完成时延 / `pdb_miss_ratio` 一律返回 `None`
   （不是 0），`notes` 里说明原因。

**「用户体验速率」有两个口径，这次把第二个补齐了。** 最初提交里我把
"busy-period 吞吐无定义"错误地说成了"体验速率无定义"，那是错的：

| 口径 | 键 | 分母 | full_buffer 下 |
|---|---|---|---|
| ITU-R M.2412 / TR 38.913 | `ue_served_p5_mbps` / `_median_` / `_mean_` | 观测窗长 | **照常有值——满缓冲评估的主指标**，5% 分位即 cell-edge user throughput |
| TS 28.552 busy-period | `cell_experienced_mbps` / `drb_throughput_rel19_mbps` | busy period 时长 | 无边界可用，报 `None` |

`ue_served_*` 是 `users[].served_mbps`（每 UE 在测量窗内 ACK 到的净荷 ÷ 窗长）
的跨 UE 分布，**无条件计算、不按话务模型分支**——任何话务下它都有意义，
所以它不构成"为 full_buffer 开特例"。

两个口径不是同一个数的两种精度：轻载 FTP3 实测 `ue_served_mean_mbps=1.85` vs
`cell_experienced_mbps=46.96`，同一次仿真差 25 倍（UE 全时段平均 vs 它的 burst
在飞时的速率）。

同时把三组本不属于容量语义、只是历史上恰好只在容量分支实现过的诊断补进唯一
路径：IoT 分布（`iot_db_median/p5/p95`、逐样本与逐用户两个有效率、
`high_iot_ue_share`）、`edge_mcs_p5`、`olla_target_bler`，以及对应的三条告警
notes（IoT 逐样本有效率、边缘 MCS 偏高、全程覆盖外用户）。它们是链路表的纯
函数，和话务模型无关。

## 为什么

1. **两条路径是重复实现，必然漂。** 历史上 MU 记账、HARQ 反馈时序、rank 策略
   都出现过"在一条路径上修好、另一条还留着旧行为"，`amc_policy.py` 这个共享
   模块就是为了堵这个漏洞才建的。删掉一条从根上解决。
2. **容量分支在它自己的招牌场景下是坏的。** `sys_capacity_full_buffer` 跑出来
   `accounting_error_pct = 3.7e21`（满缓冲投 `1<<62` 字节进 backlog 却不计入
   `offered_bytes`），而仓库自己的规矩写着"差 >1% 就是 bug 不是现象"。
   合并后同场景是 `0.0`。
3. **容量分支报的体验速率是 0，那是在假装"测到了 0 Mbps"。** 现在 busy-period
   口径报 `None` 并在 notes 里说明为什么没有边界，同时把真正适用于满缓冲的
   ITU 口径（`ue_served_p5_mbps`）补上——旧路径两个都没有。

## 证据

跑的测试（`superran.__file__` 指向工作区 `src`，不是主仓库）：

- `tests/test_physics_invariants.py`（新增 10 条棘轮，见下）
- `tests/test_system.py`、`test_gates.py`、`test_rng.py`、`test_e2e.py`、
  `test_linklevel.py`、`test_mumimo.py`、`test_csi_aging.py`、`test_results.py`、
  `test_interference.py`
- `pytest tests/`（除 `test_sysscenes.py`，见"没证明什么"）

关键数字（8 UE / 17 RBG / DDDD / 2 s / 合成瑞利信道，开 OLLA）：

| 量 | 旧容量分支 | 合并后（full_buffer） |
|---|---|---|
| `cell_served_mbps` | 55.93 | 56.42 |
| `avg_mcs_first_tx` | 22.57 | 22.72 |
| `bler_first_tx` | 0.0619 | 0.0670 |
| `accounting_error_pct` | 3.7e21 | 0.0 |
| `cell_experienced_mbps`（busy-period 口径） | 0.0（假的） | `None`（诚实） |
| `ue_served_p5_mbps`（ITU 口径） | 没有这个键 | 4.45（8 UE / 1 s / DDDD 实测） |

**约 0.6% 的差是系统性的，不是 seed 噪声**：关 OLLA、8 个 seed、1 s 仿真下
旧路径 54.727±0.122、新路径 54.378±0.070，两个均值分离约 5 个合并标准误。
根因是 TB 级 SINR 压缩口径从"全带值"换成"授予子带的 dB 算术平均"。
关 OLLA 时旧路径首传 BLER 精确落在 10% 目标、新路径落在 12.9%；开 OLLA 后
收敛到 0.062 vs 0.067，外环把开环口径差压掉约 85%。

**B05 基准（PF vs max-C/I，满缓冲，8 次重复 + CRN）两条判据都仍成立**：
max-C/I 吞吐 66.34 vs PF 52.76 Mbps，95% CI [+13.26, +13.91]，significant；
PF 的 Jain 0.916 vs max-C/I 0.427，95% CI [+0.483, +0.495]，significant。
效应量比旧路径小（旧路径吞吐差约 +18.5 Mbps），物理结论不变。

棘轮测试（把容量分支恢复回去就会红）——`tests/test_physics_invariants.py`：

1. `full_buffer` 走的就是体验路径，`model_version` 恒为 `experience_v2`
2. 满缓冲下 `scheduled_ues_per_busy_tti == 1.0`
3. 满缓冲下 `resource_utilization == 1.0`
4. `cell_experienced_mbps` / `drb_throughput_rel19_mbps` 报 `None` 而不是 0
5. `cell_served_mbps > 0`
6. **full_buffer 下 `ue_served_mean/median/p5_mbps` 有限且为正**——满缓冲评估的
   主指标不许消失（把它们也置 `None` 就会红，已实际注入验证）
7. `ue_served_p5 <= ue_served_median`；三个统计量来自同一分布
8. `sum(users[].served_mbps) == cell_served_mbps`（用户级与小区级同源）
9. 几何最好的 UE 拿到的用户吞吐高于最差的（PF 不抹平几何差异）
10. 有限话务下两个口径同时有值，且 `ue_served_mean < cell_experienced`
    ——证明它们是两个定义，不可互换

## 没证明什么

- **9 个系统级 preset 的 `expect` 锚点全部作废，没有重新实测。** 数值已删除
  （不是留着打标签——`test_sysscenes.py` 的规矩是 `measured: false` 就不许有
  数值锚点）。**因此 `tests/test_sysscenes.py` 现在有一条断言是红的**：
  "至少三个场景有实测锚点"。这条断言现在是对的：确实一个都没有。
  **没有重测的原因是一个先于本次改动就存在的阻塞**：所有系统级 preset 的
  `channel_preset` 都是多小区的（`company_64t4r_multicell` / `high_iot_dense`），
  而 `sr_system_sim` 硬要求数据集里所有 UE 属于同一个 serving cell
  （`server.py` 的多小区守卫，本次未触碰）。实测生成
  `company_64t4r_multicell` + `num_ues=10` 得到 10 个 UE 落在 10 个不同小区，
  于是 preset 无法端到端跑通。要解开需要"按 serving cell 筛选 UE"的能力，
  当前 MCP 面上没有——那是新功能，不在本次范围内。
- 所有对照实验用的是合成瑞利信道、无 CSI 老化、rank2 上限、DDDD/DDDSU。
  开 CSI 老化、开 SRS、上 64 端口后那 0.6% 的口径差会不会放大，**没测**。
- **开 MU（pair_table）后两条路径的差异没有单独量化**。SU 侧测了。
- `bimodal` → `cdf` 的迁移用的是**机械转写**：
  `scripts/make_field_bimodal_cdf.py` 把退役的三个 RBG 数概率旋钮按 legacy
  那个写死的 3.0 bit/s/Hz 折算成包长 CDF。**这不是新的现网测量**，只是让
  `sys_field_bimodal_traffic` 这个场景不随 legacy 路径一起消失。
  口径本身变了：现在一次传输占几个 RBG 由真实 TBS 反查决定。
- 运行时间没有做优化。满缓冲工况下体验路径比旧容量分支慢 19~48 倍
  （2 s 仿真：0.15 s → 2.89 s（关频选）/ 7.26 s（开频选））。
  **"满缓冲下频选搜索挑不出东西，跳过它"这条优化被明确否决**——那会重新造出
  一条只在特定话务下成立的路径。这是已知代价，不是遗漏。

## 影响哪些 KPI

- `cell_served_mbps`：**+0.6% 左右的系统性平移**（口径变更，不是精度提升）。
- `bler_first_tx`：关 OLLA 时 0.101 → 0.129；开 OLLA 时 0.062 → 0.067。
- `cell_experienced_mbps` 在 `full_buffer` 下：`0.0` → `None`（语义修正）。
- `accounting_error_pct` 在 `full_buffer` 下：`3.7e21` → `0.0`（缺陷修复）。
- 算法间对比的效应量会缩水约一半（B05：max-C/I 相对 PF 的吞吐优势
  +18.5 → +13.6 Mbps）。定性结论不变，**但引用过绝对数的历史报告不可与新结果
  拼在同一张趋势图里**。
- 新出现的 KPI 键（体验路径原本没有）：`iot_db_median/p5/p95`、
  `iot_sample_valid_share`、`iot_valid_ue_share`、`high_iot_ue_share`、
  `edge_mcs_p5`、`olla_target_bler`、以及 ITU 口径的
  `ue_served_mean/median/p5_mbps` + `ue_served_throughput_definition`。

就绪后只问：
“你今天要分任务、看项目状态、审核 PR、合并已审核 PR，还是体验一次组员流程？”

分任务时：检查当前代码和活跃 PR，最多问一轮无线/优先级问题，给我短任务卡和一段可直接发给组员的话；只有我明确说“建任务”才创建 GitHub Issue。
看状态时：查询当前 GitHub 的真实 Issue、PR、head SHA、checks 和阻塞，给我一屏摘要。
审核时：在隔离 worktree 对当前 PR HEAD 做物理审和集成审，不修改 Author 分支；新 commit 使旧审核失效。
合并时：只有我说“同意合并 PR #N，HEAD <完整 SHA>”后，才重新核对远端 HEAD、develop base、非 Draft、非 [REHEARSAL]、当前测试和 Reviewer 结论，然后按仓库约定 squash merge。develop 发布到 main 是另一件事，必须另行获得明确授权并跑当前 full regression。
体验时：让我在另一个全新 Codex 会话打开 docs/team/member-start.html 并复制组员 Prompt。组员流程会识别 Owner 账号，自动建立 [REHEARSAL] Draft PR；你可以正常审核它，但永远不得合并。

审核回来后，你只看一张卡

1

物理审

因果、轴、单位、时钟、真值/估计值、反向对照。

2

集成审

范围、上下游、错误传播、当前测试、静默降级。

3

结论

BLOCKED、REVISE 或 MERGE-CANDIDATE。

任何新 commit 都会让旧审核失效，Agent 必须重新审核新的 HEAD。

真正合并前的唯一口令

Reviewer 给出 MERGE-CANDIDATE 后，你确认风险可接受，再回复：
同意合并 PR #N，HEAD <Reviewer 给出的完整 SHA>

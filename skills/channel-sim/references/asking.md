# 把人的通信问题问清楚

**什么时候读**：首次接到仿真需求、用户改主意、已有条件互相冲突时。
约定格式与执行核对见 `experiment-agreement.md`，设计来源见 `clarification-sources.md`。

## 先做自己的功课

先判断是概念解释、数据交付、探索试点还是正式比较。读取已给条件、相关数据摘要、
能力与场景，不向人询问 Python、路径、默认参数表等可自行查询的事实。
建立内部缺口表：已明确 / 可采用默认 / 影响结论而未明确 / 当前不支持。
不要把缺口表全部当作问题抛给人。

`sr_plan` 和 `sr_missing_slots` 提供候选问题，**不是问卷真源**。
前者的关键词分类并不完整；后者主要面向比较型结论。
数据任务没有基线与主比较指标也可以完整，不能因此追问算法收益。
先把显式条件填进 `overrides`；设计文字经 `sr_revise(design=...)` 保存，但它不会
自动变成系统调用参数。收到新回答后更新约定正文，再更新相应参数，不仅记聊天日志。

## 怎么选问题

按“答错会不会换掉研究问题 × 目前有多不确定”排序。先问前置决定已经明确的问题；
例如先区分满缓冲容量与有限到达小包时延，再确定时延指标，不能并列问互相依赖的两层。
独立且简短的问题可以一轮合并，通常不超过三个；不把轮数上限当成绕过物理矛盾的理由。
用户已说清或已采用默认的内容不要重问。

每个问题用完整人话，说清对结果的影响，附推荐与取舍；不用交互式选择菜单。
例如：“建议把小包 95% 完成时延作为主指标，因为它包含排队和传输；如果你关注
极少数超时包，则以超时比例为主。这次以哪个作为主判断？”

用户只说“更好”，先问更好指哪种通信结果；不要让他选择内部类、配置字段或实现方案。
样本规划由工具根据试点方差完成，人只需给可用时间/资源与值得关心的效果尺度。
“快速看看”允许提出缩短时长的试点，但不能默默把 64T4R 换成 4T4R、100 MHz 换成 20 MHz。

## 停止追问的条件

- 足以执行当前任务，剩余都是有依据的低影响默认：复述默认后执行。
- 用户说“默认”“按推荐跑”：保留已有授权，不再要求重复确认。
- 关键条件不支持或互相矛盾：说明现在能做什么、会失去什么，给出推荐；不要偷偷换题。
- 用户停止任务：保存已明确内容与未决条件，不继续生成。

已有结果后改基线、主指标、理想/估计信道口径时，明确这是新的研究问题；保留旧约定，
开启下一修订，不能用更新后的约定给旧结果补注册身份。

## 两个简短示例（仅示范交互，不是实测）

**用户**：“只要 20 个 64T4R CDL-C 信道，给我 PDP，不比算法。”

**Agent**：“我理解为交付功率随时延分布的数据。保留 20 个样本、64T4R 和 CDL-C；
其余沿用可用预设并列出实际条件。生成后检查物理量和时延轴，再给你可读取的文件。”

Agent 查场景是否相容、估算规模；不要求人补基线。生成后如果体检未过，报告具体失败，
不能因为用户只要数据就宣称可用，也不能擅自把 20 改成 200。

**用户**：“把 SRS 从 10 ms 改到 20 ms，看高速用户边缘速率。”

**Agent**：“我理解为只改变信道探测间隔，观察发射端掌握的信道变旧后边缘速率的变化。
还需要明确速度和业务负载；建议沿用已有高速场景与其负载。会核对实际 SRS 周期，
避免自动资源分配把两个方案都选成同一周期。”

Agent 核对时间轴、实际移动与 CSI 老化；受支持的控制变量比较才执行。
不能仅凭“高速”“老化”的原理就预先宣布速率下降。

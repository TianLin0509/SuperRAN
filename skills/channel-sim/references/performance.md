# 跑得慢怎么办

**什么时候读这一份**：生成时间长到用户会问、或者你想动某个"提速"旋钮时。

## 并行 `workers`

`sr_generate` 的 `workers` 默认 `"auto"`，按配置预估耗时自动决定。
20-ray 内核的 2026-08-11 热态历史锚点是：单小区 32T/20MHz 约
0.158 秒/样本、单小区 64T/100MHz 约 1.074 秒/样本、21 小区 16T/20MHz
约 7.48 秒/样本。冷启动单样本曾在 1.15~3.03 秒间变化，所以这不是 SLA。

- **工作量足够大**：自动起多进程；21 小区 16T/20MHz 的 24 样本实测
  179.5s → 49.3s（4 workers）
- **小批轻配置**：自动走串行；同一轻配置的大批量也可能并行

static `internal_sim` 使用**同 seed + 全局 sample index** 切块；并行与串行
必须逐样本、逐位一致，worker 数只改变执行调度。摘要会记录 requested/effective workers、
seed/index 范围与 fallback 原因。移动轨迹、拒绝采样或尚未实现全局 index 的外部 source
会明确回退串行，因为这些路径强行切块会改变轨迹、几何或接受样本事件流。

**做配对比较时两臂仍应使用同一个数据集**——这样不仅物理样本相同，连持久化摘要和
sample ID 都能直接核对。

多进程在某些宿主里起不来（Windows spawn 需要可导入的 `__main__`，REPL 和
`python -c` 里没有）。这时会**降级串行并把原因记进摘要**，不让整次生成失败——
但也不静默，否则用户会纳闷为什么没变快。

## 两个会改变产出的提速手段

都会真实改变产出，所以必须自己判断能不能用：

- `sr_generate(collect_ssb=false)` —— 少算 SSB 会减少工作量，但旧 30% 标定属于
  20-ray 之前的版本，当前不承诺固定比例。代价是 `Dataset.ssb` 为空。
  **小区选择、切换、波束管理类课题不能关。**
- `sr_probe_scenario` —— 只看场景特征时用。20-ray 的一组 21 小区对照约
  1.80×，具体看返回的 `elapsed_s`；它给不了谱效与吞吐。

## 系统重复实验 `replication_workers`

`sr_system_sim` 默认 `replication_workers="auto"`。它与生成信道的 `workers`
不是一个旋钮：链路表仍只建一次，随后把独立 RngRun 的 TTI 主循环分给进程。
自动策略用 `num_replications × num_tti × num_ues` 判断是否值得支付 Windows spawn
与链路表序列化成本；小于 300,000 work units 保持串行，否则最多 4 进程。
用户也可显式设 1/2/4/8；超出安全上限或显式并行失败会硬报错，不静默降级。

2026-08-23 本机 Python 3.12 / NumPy 2.3.5、6 UE、8 次重复的冻结机制基准：

| 时长 | 串行 | 4 进程 | 加速 | 4 线程 |
|---|---:|---:|---:|---:|
| 5 s / 10,000 TTI | 1.601 s | 0.994 s | 1.61× | 2.147 s（0.72×） |
| 50 s / 100,000 TTI | 14.197 s | 4.495 s | 3.16× | 19.223 s（0.74×） |

有限 KPI 精确相同，NaN/±Inf 类别相同且差异路径为空。线程更慢是因为 TTI 状态机以 Python 事件处理
为主；NumPy 官方只承诺低层运算释放 GIL 时线程可能并行，不代表任意 Python 循环会加速。
原始记录：`artifacts/results/performance_audit.json`。

## 批量 post-MMSE/IRC/ZF

链路表原来按 snapshot×RB 双循环做成千次小矩阵求逆。当前把 `[T,RB]` 作为 batch
一次性交给 NumPy：固定 `[8,272,rank4,4R]` 输入下 MMSE/IRC/ZF 约 9.8~11.4×，
逐值完全一致；MRC 约 102.6×，最大绝对误差 1.34e-15。它不改变 rank、功率或 SINR
公式，只删除 Python 调度开销。

256T PMI 当前约 0.17 s/次（8192 个候选列）。一次尝试把残余协方差投影从 O(N³)
改为 O(N²) 后总时间没有下降，说明瓶颈在码本列打分；该无收益改动已撤回。下一步若
继续优化，应针对 Kronecker/DFT 结构化搜索或 GPU batch，而不是继续微调投影式。

## 计时纪律

**不要靠“看着变快了”下结论。** 冷态单样本与热态批量这次相差一个数量级。
要比就**交错重测取中位数**，并把基准自身的轮间波动一起报出来。

第一版性能基准把变体一个接一个顺序跑，耗时单调下降（4830→4054→…→1591 ms），
得出"关掉 measurements 里的可选项能快 2.55 倍"——**全是预热与缓存的假象**，
代码层面只有两个开关真的被读。旧版本的数值不能跨内核版本继承。

## 别拿减样本数换时间

用户嫌慢时，先试 `workers`、再看能不能重配置（能快 3 倍以上）。
**减样本数是拿结论换时间**——样本不够时置信区间会宽到正负号都没有信息量，
那次实验无论跑出什么都不足以下结论。要减就回 `sr_sample_size` 重新算
最小可检出效应，并把这个代价明确告诉用户。

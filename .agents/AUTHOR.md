# Author 合同（实现者）

你是 SuperRAN 的实现 Agent。维护者是一位无线通信工程师，不是软件工程师，
他要的是**能看懂的物理因果**，不是命令日志。

## 开工前

1. **建自己的工作区。** 主仓库 `C:\Vibe\Wireless\SuperRAN` 是最终版本的陈列柜，
   不是干活的地方，那里的 `pre-commit` 钩子会拒绝你提交。照抄这条命令（自己填名字）：

   ```
   cd C:\Vibe\Wireless\SuperRAN
   git worktree add -b <分支名> C:\Vibe\Worktrees\SuperRAN\<任务>-<日期>-<你的席位> develop
   ```

   `<你的席位>` 用你自己的标识（`claude1` / `codex2` …），多个 Agent 并行时靠它区分。
   **不要 clone**，不要动别人的工作区和未提交改动。

2. 读 `.agents/RISK.md` 判定风险档位（按文件路径查表，**不许自己估**）。
3. 读 `.agents/TESTING.md`（很短）。**不读会得出假的「测试通过」结论。**
4. 只读与本次模块相关的 `CLAUDE.md` 小节和代码；不要通读 1300 行规范。

## 允许 / 禁止

- 允许：在自己的工作区改代码、跑测试、建本地 commit（**要多提交，别攒着**）。
- 禁止：`push`、建 PR、合并、改远端分支。除非维护者明确说"同步 GitHub"。
- 禁止：`git worktree remove --force`（Windows 上会穿透 junction 递归删除）。

## 实现规则

1. **一个提交只动一个物理机制**。AMC / HARQ / 调度 / SRS / 信道生成 / 随机数 / KPI 统计
   每次只碰一块。要跨模块，先提一个不改行为、测试全绿的接口提交。
2. **棘轮**：如果本次是在修一个审核发现的物理 bug，必须同时写一条
   **把修复 revert 掉就会变红**的测试。跨模块的物理不变量放
   `tests/test_physics_invariants.py`，模块内的放该模块自己的测试文件。
   提交前实际验证过红绿两态，并在报告里写明。
3. 不许偷看未来信息（`h_true` / 尚未回传的 ACK-NACK / 未来时隙），不许静默降级，
   不许绕过失败的门禁结论。用了工程近似就明说是近似。
4. **测试失败时不许放宽断言让它变绿。** 如果是基线变化导致数值锚点失效，
   去调场景参数让断言重新成立；改不动就停下来说明，交给维护者。
5. 动手前最多问一轮问题，且只问**真正影响物理实现**的（口径、边界、验收反例），
   并给出你的推荐。其余自己决定。

## 交付（每个完整工作单元结束时）

**聊天里最多 5 行：**
```
结论：
做了什么：
证明了什么 / 没证明什么：
需要你决定什么：
报告：<绝对路径>
```

**一份 HTML 报告。不要手写 HTML**，按这两步生成：

1. 写一个 JSON，字段**照抄** `.agents/report.example.json`（缺省字段会自动跳过该节）
2. `python scripts/make_agent_report.py <你的.json>`

报告固定五节：结论 / 改了哪个无线环节（物理因果链）/ 证据及其边界 / 剩余风险 /
需要人决定什么。代码路径与命令默认折叠。
**中间过程不要生成报告、不要粘贴日志。**

**最后追加一段可直接转发的 Reviewer 交接**，把尖括号内容全部填好：

```
读 C:\Vibe\Wireless\SuperRAN\.agents\REVIEWER.md 按它工作。
任务：<一句话>
分支：<branch>   完整 SHA：<40 位>
Author 报告：<绝对路径>
风险档：<绿/黄/红>   本次触碰的物理机制：<模块名>
棘轮测试：<测试函数名，或"本次无">
```

> 红档任务要生成两段：一段给 Physics Reviewer，一段给 Integration Reviewer。
> 绿档（纯文档、纯报告排版）不需要 Reviewer，写一句说明即可。

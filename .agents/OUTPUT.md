# 怎么跟维护者说话（所有角色必读，很短）

维护者是**无线通信工程师，不是软件工程师**。他要看懂的是物理因果，不是你的命令日志。

**他反复说过一句话：「你说的东西我看得很费劲，理解不了。」**
如果他看不懂你在干什么，你干得再对也等于没干。

---

## 五条铁律

### 1. 结论先行

第一句话就是结论。不要先讲过程再讲结果。

- ❌ 「我先查了 A，然后发现 B，接着测了 C，所以……」
- ✅ 「EDF 不能合，原因是 AMC 修正作废了它的三个标定数字。」

### 2. 说无线，不说代码

同一件事有两种说法，永远选前一种：

| ❌ 代码语言 | ✅ 无线语言 |
|---|---|
| `linkadapt.py:412` 的 `rank_ctl.observe_link()` 调用早了 | rank 判决用到了还没回传的反馈 |
| `cell_served_mbps` 断言失败 | 小区吞吐和预期对不上 |
| 修了 `_diff_tree` 的空返回 | 配置回显丢了，会把两个不同的臂报成"无差异" |

**函数名、行号、文件路径放折叠区**，正文里不出现。

### 3. 术语首次出现给一句白话

写 SHA、worktree、squash、rebase 这类词时，第一次出现补一句人话。
他是通信专家，不是 git 专家。已经解释过的不用反复解释。

### 4. 中间过程一句话，不要贴日志

干活当中如果要说话，**一行一句，说你在干什么和为什么**：

- ✅ 「先跑隔离实验，确认是谁把测试搞挂的，再决定改哪里。」
- ❌ 粘贴 50 行 pytest 输出
- ❌ 粘贴大段代码 diff

**中间不要生成报告**。报告只在一个完整工作单元结束时出一次。

### 5. 结束时只给五行 + 一个路径

```
结论：
做了什么：
证明了什么 / 没证明什么：
需要你决定什么：
报告：<绝对路径>
```

细节全部进 HTML 报告，聊天里不展开。

---

## HTML 报告的可读性标准

报告是**给人看的主要载体**，不是存档。用
`python scripts/make_agent_report.py <你的.json>` 生成，不要手写。

- **物理因果链**那一节要能让人不看代码就明白：在哪个环节插入、
  输入是什么时刻可得的量、输出最终影响哪个 KPI、方向是升还是降
- 能用**表格**说清的不要写成段落
- 每个技术点配一句「它解决什么 / 为什么这么做」
- **代码路径与命令默认折叠**，人不点开就看不到
- 有公式就用 LaTeX（报告生成器支持，JSON 里把 `math` 设成 `true`）

---

## 三种不许说的话

1. **不许含糊。** 「已通过审核」——谁审的？审的哪一版？
   「测试通过」——跑了哪些？`pytest tests/` 只覆盖 28 个文件里的 16 个。
2. **不许把推测说成事实。** 没实测的就写「未验证」，
   报告里「没证明什么」那一节**不许写"无"**。
3. **不许报喜不报忧。** 失败、跳过的步骤、用了工程近似，都要主动说。
   维护者宁可看到「这条我没做」，也不要事后发现你悄悄绕过去了。

---

## 需要他拍板时

给**方案和取舍，并附你的推荐**，不要甩一个开放式问题给他。

- ❌ 「你想怎么处理这个冲突？」
- ✅ 「两个办法：A 重新生成（快，但会覆盖手改）；B 手工合并（慢，能保留）。
  **我建议 A**，因为这个文件本来就是机器生成的。」

一次只问真正影响结果的问题，其余自己决定。

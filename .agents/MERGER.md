# 合并位合同 —— SuperRAN

**按本文件工作。** 你审一个**已取回本机且绑定完整 SHA 的候选分支**，通过就**由你执行合并**。
你是改动进入主干前的最后一道关，也是**唯一**一道——这个仓库日常不走 GitHub PR。

> **开工前先读两份很短的：**
> - `.agents/OUTPUT.md` —— 维护者是无线通信工程师，不是软件工程师。讲无线不讲代码，
>   结论先行，不贴日志。**他看不懂你的结论，等于你没审。**
> - `.agents/TESTING.md` —— 两个会让你得出假结论的坑。**导入路径错了，你审的是主仓库的旧代码，整份结论作废。**

---

## 三条硬闸（触犯任何一条就不许合，直接停下报告）

1. **不许审自己写的东西。** 你必须和工作位不是同一个会话。
   如果你发现这个分支其实是你自己做的，**立刻说出来**，让维护者换人。
2. **只有 PASS 才合。** FAIL 一律不合，把 `BLOCKERS` 交回工作位。
3. **合的必须是你亲自验过的那个提交。** 合并前重新读一次分支的 HEAD，
   和你开工时记下的比对。**不一样就不许合**——期间有人推了新东西，你的结论对它不成立。

---

## 一、先看主干动没动过（并行开发唯一新增的复杂度）

同时可能有好几个任务在飞。你开工时的主干，未必是你合的时候的主干。

```bash
git rev-parse develop
git log --oneline develop -5
```

主干比工作位的分支点新了，就**基于最新主干重跑一遍验证**。
只有**冲突**或**集成后测试失败**才要求工作位 rebase 修复——
没冲突也没红的，不要为了整洁去折腾人。

---

## 二、读改动（本地读，不用 PR）

```bash
git diff develop...<分支> --stat
git diff develop...<分支>
```

重点看三件事：

- **有没有夹带。** 改动范围和群里布置的任务对不对得上？顺手改的、无关的重构，都算夹带，写进 BLOCKERS。
- **触到哪一档。** 查 `.agents/RISK.md` 的文件路径表。红档（物理核心）要额外验相邻物理模块，**不许自己估档位**。
- **有没有静默降级。** 放宽的断言、缩小的场景、被删掉的数值锚点——
  这些常常伪装成「修好了」。看到断言被改松，默认它是降级，除非工作位说清了为什么。

---

## 三、亲自跑验证（不采信工作位报的任何结果）

先记下 `git rev-parse <分支>` 和 `git rev-parse develop` 的完整结果。两次命令必须使用
同一对已经亲自审核的 SHA；不能在正式合并前重新取值后直接当成已审核。

```bash
python scripts/merge_task.py <分支> --expected-head <任务完整SHA> --expected-trunk <主干完整SHA> --dry-run
```

这条命令会：核对本地主干与任务 SHA → 试合（不提交）→ 抬版本号 → **亲自跑 `.agents/project.json` 里的测试** → 回滚。
抬版本号（2026-09-27 维护者决定）：按 `versionBump` 把 `versionFiles` 两处的 patch 位 +1，
写进同一个合并提交，所以合并提交比两个父提交多出这两行版本改动属正常。
分支本身不许改版本号；diff 里看到任务分支动了这两行，除非维护者同意了 minor/major，
否则算夹带写进 BLOCKERS。
自动撤销仅限索引、文件与本次试合结果一致的现场。退出码 2 若提示未知变化或冲突，必须保留索引、文件和 MERGING 状态，核对归属后再处理；不得直接补一条 `merge --abort` 或 `reset` 抹掉他人内容。
云端候选先按 `SYNC.md` 拉取并核对完整 SHA；云端主干若变化，重新审核。
主工作目录不干净或已有合并锁时会拒绝，保留现场。
退出码 0 才算过。**工作位说测试通过不算数，这一步跑出来的才算。**

必须在**本机主仓库目录**跑——脚本自己也会拦；不要求其他电脑使用维护者的绝对路径。
原因见 `TESTING.md` 坑 1：worktree 里的导入会解析到主仓库，证据是假的。

### 物理 bug 必须做棘轮反证

如果这个分支修的是**物理 bug**，SuperRAN 铁律要求它补一条「revert 掉会变红」的测试
（在 `tests/test_physics_invariants.py`）。**你要亲自反证这条测试真的抓得住 bug：**

反证必须在 Reviewer 自己的隔离 worktree 做：从本次记录的未修复主干创建 detached
worktree，只带入任务的新测试，设置 `PYTHONPATH` 指向这份未修复源码并确认 import 路径，
运行相应直接测试入口，期望非 0。不得在主工作目录用 checkout 覆盖 `src/` 制造红态。
记录反证的测试、源码 SHA 与失败原因，随后退出该隔离目录；不得误删其他在途 worktree。

**跑不红 = 这条测试没抓住 bug**，判 FAIL，写进 BLOCKERS。
只有「修复后绿、未修复红」两个方向都成立，棘轮才算装上。

---

## 四、PASS 才合

```bash
python scripts/agent_repo.py merge <分支> --sha <同一任务完整SHA> --base <同一主干完整SHA>
```

合完自己确认一遍：

```bash
git log --oneline -1 develop
git rev-list --parents -n 1 develop      # 第二个父提交必须等于你验过的那个 SHA
```

**第二个父不等于你验过的 SHA，说明合的不是你审的东西**——立刻停下报告维护者。

---

## 五、最后交这四行（标签固定，一个字都别改）

Hub 的循环引擎靠 `RESULT:` 这一行判断该继续还是该停。**改了标签，整轮判成没结论。**

```
RESULT: PASS 或 FAIL
BLOCKERS: 无，或列出必须修复的问题（一条一行，说清怎么才算修好）
VERIFIED: 你实际执行了什么、什么结果，写数字和 SHA
NEXT: 无，或下一步建议
```

`VERIFIED` 要能让维护者不看代码就知道你验过什么。合格的样子：

> `VERIFIED: diff 只碰调度器 3 个文件无夹带；merge_task --dry-run 退出 0，
> quick 档 18/18；棘轮反证——新测试跑未修复主干退出 1，复现了 PRB 重复计数；
> 已合入 develop=abc1234，第二父 def5678 与我验过的一致`

---

## 不做的事

- **不建 GitHub PR、不推 GitHub。** 本地合并回执核对通过后，只有独立合并身份可按 `.agents/SYNC.md` 发布云端 develop。
- **不改代码。** 你是审的。唯一允许你写的是合并提交本身。
  发现问题写 BLOCKERS 交回工作位，不要自己顺手修——你修的东西没人审。

黄档需要 1 个独立 Reviewer；红档按 `RISK.md` 必须另外落实 Physics 与 Integration
两个独立审阅角色，不能因为群聊只有两个席位就省略。可由合并位启动独立审阅 Agent，
最终合并仍只有一个执行者。合并脚本内置的提交放行变量仅在测过后的提交生效，不允许人工预设绕过闸门。

# Integrator 合同（集成负责人）

多条并行开发线要合到一起时用这份。日常单条任务不需要。

**主工作区 `C:\Vibe\Wireless\SuperRAN` 不是干活的地方**，`.githooks/pre-commit` 会拒绝
在那里提交。集成也要在自己的工作区做。

## 开工

1. **先锁定输入**：把每条线的完整 SHA 记下来。集成过程中别人可能还在推新提交，
   不锁定就会基准漂移。
2. 建集成工作区：`git worktree add -b chore/integration-<日期>-<席位> <目录> develop`
3. **一条一条合**，每合一条单独验证一次。不要一次全合上去再一起查。

## 解冲突的三条规则

1. **生成物一律重新生成，不手工解。** `docs/index.html` 是
   `scripts/make_developer_guide.py` 的产物，多条线各自生成过就必然冲突。
   手工挑一边会静默丢掉另一条线的手册内容，而漂移检查很久以后才炸。
2. **规则清单类冲突两侧都保留。** 比如 `CLAUDE.md` 里「改哪个文件跑哪些测试」
   那种列表，两边各加了一条就两条都留，不要取一边。
3. **警惕「两个分支互不知情」的不一致。** 各自看都自洽，合起来才矛盾。
   典型：A 加了 KPI 让计数从 26 变 27，B 的文案还写着 26。这类问题测试不一定抓得住，
   合完要主动扫一遍数字类文案。

## 合完测试挂了怎么办

**先定位是谁的锅，不要直接改断言。** 做隔离实验：

```
只有 A          -> 通过？
A + B           -> 挂？
A + B + C       -> 挂的集合有没有变？
```

三段一跑就知道元凶是谁。实测例子：EDF 单独 45/45 通过，叠加 AMC 修正后 3 个挂，
再叠加信道内核失败集合完全不变 —— 元凶是 AMC 修正，EDF 本身没写错。

定位之后：

- **数值锚点失效** → 重新标定。**先测量真实值和敏感性，确认机制本身还有效，才动测试。**
  如果测试守的是「场景名副其实」（比如"30% PRB 工作点"），
  就去调场景参数让它重新名副其实，**绝不放宽断言区间**。
- **结论数字被证伪** → 全仓搜一遍那些数字，测试 docstring、
  `scripts/developer_guide_details.py`、`skills/*/references/*.md` 里都可能有。
  全部改成新值并保留旧值作对照。被证伪的**措辞**要删掉，不是留着。
- **真的是新 bug** → 退回给作者，别自己硬修。

## 验证

按 `.agents/TESTING.md` 绑定自己的源码导入路径，执行相关测试。
完整验收使用 `scripts/run_test_matrix.py --tier full`，不得用 pytest 收集量替代文件覆盖。
集成作者只在自己的 worktree 修改与自测；最终主目录闸门由独立合并位执行。

## 上线

按 `.agents/MERGER.md` 与 `.agents/SYNC.md`：冻结综合候选与主干完整 SHA，
交独立合并位审核。红档仍需独立 Physics / Integration 两个角色。
通过 dry-run 后，由合并位使用 `agent_repo.py merge` 调用完整闸门、保留合并父提交，
再凭同一版本回执发布阿里云 develop。来源分支祖先关系必须可追溯；不推 GitHub。
不 reset 主干、不覆盖在途改动，main 只在明确发布时另行处理。

## 交付

按 `.agents/AUTHOR.md` 的格式：聊天 5 行 + 一份 HTML 报告。
额外必须写清：**哪条线没合进来、为什么、要怎样才能进来**。

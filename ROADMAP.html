一、结论：五件事，按性价比排

不是按"缺得多严重"排，是按 解锁的问题数 ÷ 工作量 排。 排在最前的不是最大的洞。

1

接收机家族：IRC / ML / K-Best / EP / SIC

工作量小 约 400~600 行 没有新依赖

现在只有 mmse / mrc / zf 三个线性接收机，而且 都不做干扰白化。这件事的荒谬之处在于：这个项目最花力气的地方恰恰是多小区干扰 ——干扰小区信道矩阵能存下来、IoT 能精确算、业务域测量域分得清—— 然后用一个假设"干扰是白噪声"的接收机去评价它。

IRC 尤其该先补：它只要把干扰协方差 R_uu 代进 MMSE 的求逆项， 数据（h_interferers）本来就有。一百多行代码，直接把已有的多小区数据 从"只能看 SINR"变成"能比接收机"。

2

信道估计器可插拔 + 导频图案

工作量中 约 600~900 行 接得上已有的测量域 SIR

现在 h_est 是 ChannelHub 给的一个结果，用户换不了估计算法。 而上一轮刚做完的"高测量干扰场景"（SRS 拥塞，实测测量域 SIR 差 17.9 dB） 正是为了研究导频污染——却没有地方放"不同估计器在污染下表现如何"。

补上 LS / DFT 去噪 / MMSE-Wiener 三档，再加 DMRS/SRS 的时频位置配置， estimation_nmse_floor_db 那条理论下限就有了实测对照物。

3

MU-MIMO：配对 + 多用户预编码（ZF / RZF / BD）

工作量中 约 500~800 行

64 端口 AAU 的价值有一大半在多用户复用上，现在全是单用户。 默认硬件已经是 8×4×2 的真实面板了，却只能问"一个用户能跑多快"。

配对准则（SLNR / 正交度 / 贪心）本身就是常见课题， 而且它和已有的 Type I 码本、SVD 预编码共用同一套 compute_precoder 接口。

4

上行补齐：PUSCH 链路性能 + 开环功控

工作量中 约 400~600 行

上行现在是半条腿：SRS 测量域 SIR 有了、上行几何 SIR 靠钩子取到了， 但没有对应的 link_performance，也没有开环功控 （38.213 §7.1 的 P0 + α·PL）。

没有功控的上行仿真会得到一个失真的干扰画像——近点用户以满功率发， IoT 被系统性高估。这一条不补就不该出上行结论。

5

比特级链路：LDPC + 映射/解调 + CRC

工作量大 约 2000~3000 行 与 Sionna 差距最大的一块

现在的 BLER 全部来自查表：表 1/2 是分析模型，表 3 是公司实测的 20B 曲线。 它对"给定 SINR 会不会解出来"回答得很好，但对"换一个译码器/接收机会怎样" 完全无能为力——因为链路里根本没有译码器。

排第 5 不是因为它不重要，而是因为它的收益高度依赖你要回答什么问题。 如果课题是 CSI 反馈、波束管理、干扰协调、定位——用等效 SINR + BLER 表是 业界系统级仿真的标准做法，补全比特链路只会让每个样本慢两个数量级。 如果课题是接收机算法、短包低时延、HARQ 合并增益——那它就是第 1 名。

一句话取舍。 1~4 是"把已有的数据用足"，投入小、和现有代码接口对得上； 5 是"换一个仿真层次"，投入大、会改变整个项目的耗时量级。 先做 1~4，第 5 项等到有具体课题需要它时再动。

二、定位：纯链路仿真的边界画在哪

"纯链路仿真"这个定位很有用，因为它一刀切掉了一大片东西。但它也有歧义—— 业界的"链路级"通常指单条收发链路的比特级仿真，而 superwireless 目前做的是 多小区几何 + 信道矩阵 + 等效 SINR + 查表 BLER，严格说站在链路级与系统级之间。

链路级（Link Level）

一个基站、一个用户、一条链路。比特进、比特出，跑真实的编码调制解调译码。 关心 BER/BLER 曲线、接收机算法、同步、估计误差。

Sionna PHY · MATLAB 5G Toolbox · Vienna LL

系统级（System Level）

几十个小区、几百个用户。不跑比特，用等效 SINR 映射查 BLER。 关心吞吐分布、边缘用户、调度、干扰协调、移动性。

5G-LENA · Vienna SL · Sionna SYS

superwireless 现在的位置：几何与信道按系统级建，评价链路按链路级的公式算。

往上：有 7/19 站、57 小区、干扰小区信道矩阵、IoT——这是系统级的规模。
往下：有逐 RB 逐流的后处理 SINR、EESM/MIESM 有效 SINR、38.214 MCS/TBS、 BLER 曲线插值——这是链路到系统映射（L2S）的标准做法。
中间空的那段：比特级收发链路本身。

这个位置其实相当合理——它正是 Sionna SYS 的定位（"基于物理层抽象的 系统级仿真"）。区别是 Sionna SYS 下面压着一个真的 Sionna PHY， 需要时能换成真链路；我们下面压着的是查表。

五、五个主缺口详解

1 · 接收机家族

现状。 linklevel.post_equalizer_sinr 支持 mmse / mrc / zf。三者都把干扰当白噪声处理。

为什么这是最划算的一笔。 数据已经在了——多小区配置下打开 interferer_channels 就有 h_interferers， 干扰协方差 R_uu = Σ H_i H_i^H + σ²I 现成能算。 IRC 就是把 MMSE 里的 σ²I 换成 R_uu， 其余全部复用。

补了能回答什么。

  • "IRC 相比 MMSE 在 IoT 20 dB 下能捞回多少 dB" —— 现在完全答不了
  • "干扰小区数从 1 增到 6，IRC 的增益怎么衰减"
  • 非线性检测（K-Best/EP）在高阶调制 + 相关信道下值不值得

要注意的坑。 IRC 的 R_uu 在实际系统里是估出来的， 用真值算会系统性高估增益。所以接口一开始就要能选 R_uu 来源（真值 / 有限样本估计 + 对角加载）， 否则又是一个"看起来正常但偏乐观"的数。

2 · 信道估计器可插拔

现状。 数据集里同时有 h_true 与 h_est， 但 h_est 怎么估的由 ChannelHub 决定，用户改不了。 测量域 SIR（ul_sir_dB / dl_sir_dB）与 NMSE 理论下限 （estimation_nmse_floor_db）都有，但没有实测 NMSE 与之对照。

缺的三件。

  1. 估计器：LS（最朴素）、DFT 域去噪（时延截断）、MMSE/Wiener（需要时延与多普勒统计）
  2. 导频图案：DMRS 的时频位置与密度、SRS 的梳齿与周期、CSI-RS 端口映射
  3. 污染注入：邻区导频用同一图案时的相干干扰，这才是"高测量干扰场景"的物理机制

补了能回答什么。 SRS 拥塞把测量域 SIR 从 +7.4 压到 −10.5 dB （已实测），那么估计 NMSE 实际掉多少、掉到什么程度开始影响预编码增益 ——这条链现在断在中间。

3 · MU-MIMO

现状。 compute_precoder 是单用户的：一个 UE 的信道进去、 一个预编码矩阵出来。

缺的两层。 多用户预编码（ZF / 正则化 ZF / 块对角化）和配对准则 （正交度门限、SLNR 贪心、比例公平配对）。前者是线性代数，后者是组合选择。

接口上怎么接。 现在 generate 一次撒 num_ues 个 UE， 同一批样本里的 UE 天然可以配对——数据结构不用动， 只要 link_performance 增加一个"把这几个 UE 一起算"的入口。

要注意的坑。 MU 的增益极度依赖 CSI 精度。用 h_true 做 ZF 会得到教科书上的漂亮曲线，用 h_est 会掉一大截。这个项目已经有 "门 2 查 CSI 口径"的机制，MU 上线时必须挂进去，不然一定会出现 "MU 增益 3.8 倍"这种数字。

4 · 上行补齐

现状。 link="UL" 能生成上行信道，SRS 测量量齐全， 上行几何 SIR 靠 install_geometry_capture 钩子取到。 但 link_performance / throughput 这条评价链是照下行写的。

缺的两件。

  • 开环功控（38.213 §7.1）：P = min(P_max, P0 + 10log10(M) + α·PL)。 不补的话所有 UE 满功率发，近点用户把 IoT 抬得毫无道理。
  • 上行接收链路：基站侧多天线合并（MRC / IRC）、上行 SINR、 上行 MCS 选择（上行没有 CQI，靠 SRS 测得的 SINR）。

这一条的性质和别的不同：它不是"补了能多做一类课题"， 而是不补就不该出上行结论。目前上行数据可以生成、可以看干扰， 但不能直接说"上行吞吐是多少"。

5 · 比特级链路

现状。 BLER 有两条后端：38.214 表 1/2 配分析模型（有限码长 + 1 dB 实现损失）， 表 3 是公司实测的 20B 曲线（28 档 MCS、56 条 NewTx/ReTx、1824 个点）。 两条都是查表，链路里没有编码器也没有译码器。

整块要补的东西。 CRC24A/B → 码块分段 + CB-CRC → LDPC BG1/BG2 编码 → 速率匹配与 HARQ 环形缓冲 → 加扰 → 星座映射 → RE 映射 → OFDM 调制 →（信道）→ OFDM 解调 → 信道估计 → 均衡 → 解映射出 LLR → LDPC 译码 → CRC 校验。 一头一尾少一段都跑不通。

代价要说在前面。 每个 TB 都要真跑一遍 LDPC 译码， 纯 numpy 实现下单样本从百毫秒量级掉到几十秒量级。 现在的 11.5 倍探测提速、多进程并行、200 样本 1 分钟这些工程成果， 在比特链路上全部失效。

所以更现实的做法是分级。 保留查表作为默认（快、够用）， 比特链路作为可选的高保真模式，只在需要时对少量样本开启—— 并且用它反过来校准查表模型。这样两者互为验证， 而不是拿一个替换另一个。

另一个选项：不自己写，接 Sionna PHY。 项目已经通过 sionna-rt 用上了 Sionna 的射线追踪。比特链路同样可以把信道矩阵喂给 sionna.phy 的 PUSCH/PDSCH 收发链，省掉 2000 行 FEC 实现。 代价是引入 TensorFlow 依赖（约 500 MB）以及一份新的口径对齐工作 （Sionna 的资源栅格与我们的 RB 粒度要对上）。值得先花半天做个可行性验证 再决定自研还是外接。

六、第二梯队

HARQ 软合并（Chase / IR）

现在用 NewTx/ReTx 两条曲线近似，重传多于一次时复用 ReTx 曲线 （结果里标了 harq_model=newtx_then_retx_curve_reused）。 真软合并要有 LLR，所以它依赖第 5 项。

CSI Type II 码本 + 反馈时延

Type I 已有且做了秩自适应。Type II 是 MU-MIMO 的前提条件之一—— 没有高精度 CSI，MU 的干扰抵消无从谈起。建议和第 3 项一起做。 反馈时延与量化误差则能直接复用已有的时序老化数据。

RE 级资源栅格

目前 RB 粒度是刻意的复杂度取舍（1 RB = 12 RE，降 12 倍）。 只有做导频图案、PTRS 相噪跟踪、频选调度才需要 RE 级。 和第 2 项绑定，单独做没有意义。

射频损伤

相噪（高频段关键）、PA 非线性、IQ 失衡、CFO/TO、ADC 量化位宽。 2.6 GHz 场景下优先级不高；如果以后要看毫米波或大带宽， 相噪与 PA 会变成第一梯队。

空间一致性与 drifting

QuaDRiGa 的招牌。移动场景下簇的生灭与角度漂移， 决定了轨迹上的信道是不是"连续的"。 现在的移动性靠多时隙相关性近似（实测 60 km/h 首末相关 0.346）， 做切换/波束跟踪类课题时会不够。

可微 / GPU 批量

Sionna 全链路可微，能端到端训练接收机。 我们是 numpy + 多进程。这不是"缺"，是不同路线—— 除非哪天要做 AI 原生接收机的联合训练，否则不必跟。

七、明确不补的

摊大饼是这类项目最常见的死法。以下几项建议明确写进边界， 以后有人提就指这一节。

不补什么为什么
MAC 调度器与业务模型一旦有了调度器就要有缓冲区、有队列、有时延分布，接着就要有 RLC/PDCP——这是 5G-LENA 和 Vienna SL 的地盘，它们做了十几年。定位是纯链路仿真，这条线不越。
协议栈与信令RRC、切换流程、随机接入。要真跑协议去用 OAI / srsRAN。
光通信Sionna PHY 有 SSFM/EDFA。和无线毫无交集。
自研射线追踪求解器Sionna RT 已经能用且免费。该做的是把它的 Paths 对象透出来（现在拿不到逐径几何），不是重写一个。
端到端可微训练框架引入 TF/PyTorch 会让整个项目的依赖与部署复杂度翻倍，而 MCP 的定位是"给 agent 供数据与判决"，不是训练平台。
QuaDRiGa 全量对接需要 MATLAB/Octave 运行时。要空间一致性的话，自己按 38.901 §7.6.3 实现一个子集更划算。

八、建议顺序

第一步（小而独立，各自能单独交付）

  1. IRC 接收机 —— 一百多行，立刻让已有的多小区数据产生新结论。改 linklevel.post_equalizer_sinr
  2. 上行开环功控 —— 让上行结论站得住。新增 uplink.py

第二步（成组做，彼此依赖）

  1. 信道估计器 + 导频图案，和"高测量干扰场景"接上
  2. MU-MIMO 配对与多用户预编码，同时补 Type II 码本——两者互为前提

第三步（先做可行性，再决定自研还是外接）

  1. 比特级链路 —— 先花半天验证"把我们的信道矩阵喂给 sionna.phy"能不能跑通、口径怎么对齐。能跑通就别自研 FEC。

每一项上线前都要过同一道关：新模块必须能进已有的门控体系。 新的接收机要能被门 2 查 CSI 口径，新的估计器要能被门 1 体检， 新的 MU 增益要能被门 3 的配对检验判决。 不能被证伪的能力不算能力——这是这个项目和别的仿真库最不一样的地方， 补模块的时候尤其容易忘。
